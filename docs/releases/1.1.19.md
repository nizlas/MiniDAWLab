# Danielssons Audio Lab 1.1.19

| | |
|---|---|
| Version | 1.1.19 |
| Date | 2026-10-07 |
| Installer | `DanielssonsAudioLab-1.1.19-Setup.exe` |
| Portable | `DanielssonsAudioLab-1.1.19.zip` |

Three arrangement / project features in one delivery: a staged, responsive project load with a
real progress window, a vertical scrollbar for the track list, and **Duplicate Track**. The
parallel live-instrument rendering from 1.1.18 is unchanged. Architecture:
`docs/CURRENT_ARCHITECTURE.md` ("Project loading is staged…", "Arrangement vertical scrollbar",
"Duplicate Track").

## Changed

- **Opening a project shows what is happening and keeps the window alive.** A modal "Opening
  project" dialog appears at once and updates through the phases — *Reading project…*, *Loading
  audio material… n of m*, *Closing previous project…*, *Preparing project…*, *Loading
  instruments… 17 of 64: VB3-II*, *Preparing tracks…*, *Restoring effects… 9 of 50: AmpliTube
  4*, *Finalizing project…* — with a determinate bar only where a count exists (never 100 %
  before the project is in), indeterminate otherwise. Audio files are decoded on a background
  thread (each unique file once instead of once per clip); instruments and insert chains are
  restored one per message-loop turn so the main window paints and the dialog updates between
  them. While a load runs: no editing, no Play, no Record (clear refusal text), no Save / Open /
  autosave, no undo / redo; the dirty flag stays clear; a corrupt file fails cleanly with the
  previous project intact and the next Open works. No nested message loop, no Cancel button.
- **The end pause is gone.** On the 100-track load test the old path ran all 50 insert chains in
  ONE deferred message after `load: complete` — about 19 s of "Not responding" with 18 AmpliTube
  4 instances at 1–2 s each. Now the chains are separate units with progress text. Measured
  (Release, 100-track copy): 45–47 s total with the dialog updating throughout; the longest
  message-loop gap is **≈ 2.2–2.7 s** and is the *first* AmpliTube 4 instantiation (its DLL load;
  later instances take ≈ 1.1 s each) — a single third-party operation DAL cannot split; no gap
  reached the 5 s "Not responding" threshold. The small TSE copy opens in ≈ 6 s.
- **Vertical scrollbar for the arrangement.** A scrollbar sits right of the track rows (below
  the timeline ruler). It drives the same scroll position as the mouse wheel, moves headers and
  lanes together, supports thumb drag and page-wise clicks in the trough, takes its range from
  the real total track height (varying row heights included), follows resize / add / duplicate /
  delete / undo / project switch, and hides when everything fits. Ruler, playhead and horizontal
  scrolling are untouched; the column is always reserved (14 px) so lane widths never jump.
- **Duplicate Track** in every track header's right-click menu, right after Delete Track, acting
  on the clicked track (also when another track is active). The copy lands directly below the
  original as "<name> — kopia" (then " 2", " 3" …), becomes the active track, gets new ids for
  the track and its clips, and carries the same clip placements / trims / MIDI notes /
  controllers / pitch bend, fader, pre-gain, pan, Mute / Off, output routing, sends, input
  assignments and MIDI To. **Record Arm and Monitor start off.** Audio, instrument, pure MIDI
  and Group tracks can be duplicated; Stereo Out cannot. Inserts and instruments are copied with
  their current state into **own plug-in instances** (unavailable plug-ins stay placeholders with
  identity + state); changing a parameter on the copy never touches the original. Audio material
  is shared (no WAV copies). Other MIDI tracks pointing at the original are neither copied nor
  rerouted; a Group copy keeps its own routing / inserts / sends without copies of its feeding
  tracks. One undo step; dirty only on success; survives save / reload. Refused while recording,
  during count-in and while playing (menu text says so).
- **Delete / Duplicate share one undo rule.** On undo and redo the instrument runtime of a
  structural step is recreated when the restored timeline contains the row and retired when it
  does not — presence decides, not the step kind.
- Header menu texts "Load VST3…", "Plugin editor…", "Plugin parameters…" now render a real
  ellipsis (they showed `â€¦`).

## Verified

- `--stability-load-progress` (new) on temp copies: the dialog showing and updating through every
  phase (PNG evidence), a 25 ms message-loop probe (max gap, counts over 0.5 / 2 / 5 s), the
  gates while loading (dirty, structural edits, Play, add track, Record refusal, undo, Save not
  writing), fraction never 100 % early, corrupt-file failure path with the previous project
  intact, reopen. PASS in Release and Debug on the TSE copy (full run incl. reopen); on the
  100-track copy the first load + failure path pass, the reopen leg hits the known AmpliTube 4
  teardown crash (see Known).
- `--stability-duplicate-track` (new, Release, TSE copy): audio row with AmpliTube 4 + a Post
  insert (DAL Mono Delay) + a send to a Group, duplicated while another row was active; instrument
  row (VB3-II, 2 clips / 97 notes, 14 112-byte state) → own host, same content and state; pure
  MIDI row routed to the instrument → same MIDI To, same notes; Group → no feeding track copied or
  rerouted; a row with an unavailable placeholder → placeholder + bytes preserved; parameter
  independence (copy 0.0 → 0.9, source stays 0.0); exactly one undo step, undo keeps the source's
  instances, redo restores with own instances; dirty flag; save / reload with all five copies;
  Stereo Out refused without dirtying. Scrollbar: range from real content with varying row
  heights, thumb drag to bottom / top, page click, wheel, header / lane alignment per row, range
  after delete / undo. Header-menu PNG written. PASS.
- `TrackDuplicateFocusedTests` (new, 23 checks): the domain step.
- Regressions (Release, TSE copy): `--stability-load-loop` ×2, `--stability-smoke`,
  `--stability-delete-loop`, `--stability-header-column`, `--stability-inserts`,
  `--stability-recover-autosave`, `--stability-midi-routing` — all PASS. Focused:
  `InputRoutingFocusedTests` 56, `TrackHeaderColumnFocusedTests` 149, `MixerFocusedTests` 107,
  `InsertPersistenceFocusedTests` 121, `WaveformReloadFocusedTests` 30,
  `LiveMidiRecordingFocusedTests` 110, `MixdownPreGainFocusedTests` 54,
  `InstrumentParallelFocusedTests` 39 — all green.
- Scrollbar thumb / trough / wheel were driven at handler level (`ScrollBar::setCurrentRangeStart`
  with notification, `moveScrollbarInPages`, `mouseWheelMove`), not by OS mouse input.

## Known

- **AmpliTube 4 teardown crash** (`AmpliTube 4.vpa+0x7675E`, recorded since 2026-10-03): still
  intermittent at app shutdown and when a project with AmpliTube instances is replaced by another
  (`removeAllPlugins`). Several regression runs ended in it *after* their PASS line; two
  (load-loop, smoke) hit it on their second load and passed on rerun. Not audited in this slice.
- Retiring a loaded 100-track project when opening another is one ≈ 15 s synchronous unit
  ("Closing previous project…"); splitting that teardown per row is backlog.
- `InstrumentParallelFocusedTests` used a busy-work constant that sat right at the pool's 300 µs
  threshold on a fast core (serial fallback → false FAIL); raised to 120 000 iterations. Test-only.
