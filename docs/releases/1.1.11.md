Fix release for live MIDI input (1.1.10). Report: `docs/LIVE_MIDI_RECORDING_2026-10-03.md`,
section "1.1.11 — field failure and fix".

## Fixed

- **The MIDI Input chosen in the Inspector could land on another track.** Clicking the speaker
  (Monitor) or R on an instrument / MIDI track header did not make that row the active row, so
  the Inspector kept editing whichever row was active before. A user who clicked Monitor + R on
  VB3-II and then picked "All MIDI inputs" configured the previously active track instead: VB3-II
  stayed silent (no input routed) and Record answered with the generic "arm a track" message.
  Monitor and R now activate the row like Mute, Power and the audio rows' buttons do.
- **The runtime now follows an Inspector pick immediately** (devices opened, routing published)
  instead of on the coordinator's next tick.
- **Record explains the real reason.** With R on but no usable MIDI input, Record refuses with
  the track name and the reason — "no MIDI Input selected", "device … is not connected
  (assignment kept)", "device … could not be opened (in use by another application?)" or "All
  MIDI inputs is selected, but no MIDI input device is connected" — never "arm a track" while the
  track is armed. Ready rows still record when other armed rows are not ready (logged).
- **Inspector status** now also says "Monitor / R is on, but this track has no MIDI Input",
  "Ready — no MIDI received yet on this track's input" / "MIDI received: N events", and the busy /
  missing-device reasons above. A device whose port was busy is retried every 2 s.

## Verified

- `--stability-live-midi` now drives the user's real controls: header cell clicks (same hit
  test and callback as the mouse) and Inspector combo picks (same `onChange`); it reproduces the
  1.1.10 failure sequence and asserts the fix, checks session vs runtime routing after each step,
  the refusal texts, a missing ("ghost") device, Device mode and All through the Inspector, and
  — on a project with VB3-II loaded — **measured audio** (−9.7 dBFS on the row's output meter)
  from a live note with the transport stopped. PASS on the 120 BPM fixture and the 180 BPM TSE
  copy.
- Still not possible here: a key press on a physical keyboard (no loopback driver; the RME port
  is opened and callback-registered, and its driver turned out to be multi-client, so the
  busy-port explanation path is verified by code only).
- Final 1.1.11 builds (Debug `build\ninja-debug\...\Debug\MiniDAWLab.exe`, Release
  `build\ninja-release\...\Release\MiniDAWLab.exe`, both FileVersion 1.1.11, ASIO enabled):
  focused tests 79 / 3225 / 149 / 47 / 56 / 49 / 121 checks, 0 failures; Debug scenarios
  live-midi (TSE copy −9.81 dBFS, fixture), midi-routing, midi-track-parity, midi-editor-move,
  inspector-panel, header-column, organ-dc, mixdown-wav, pregain, inserts all PASS; Release
  scenarios live-midi (TSE copy −9.61 dBFS, fixture), midi-routing, mixdown-wav PASS. Log
  excerpt: `docs/evidence/live-midi-2026-10-03/live-midi-scenario-run-1.1.11.txt`. The packaged
  `MiniDAWLab.exe` in the installer and zip is byte-identical to the Release build
  (SHA-256 `905282FF…494FEA`).

## Known, unchanged

- AmpliTube 4 teardown crash (`0x7675E` in `AmpliTube 4.vpa`) remains intermittent at
  shutdown / project reload; during this verification it hit once after a PASS (header-column,
  Debug) and once inside the Release live-midi "reload test copy" step on the TSE copy (the
  re-run passed). Projects without AmpliTube are unaffected.
