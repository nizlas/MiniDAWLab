# Current architecture (baseline)

This document states **what the MiniDAWLab codebase is today** — not phase history or roadmaps.

Use it alongside [ARCHITECTURE_PRINCIPLES.md](ARCHITECTURE_PRINCIPLES.md), [PROJECT_BRIEF.md](../PROJECT_BRIEF.md), and [IMPLEMENTATION_GUIDE.md](IMPLEMENTATION_GUIDE.md).

---

## Composition and threads

- **Message thread**: UI, `Session` mutations that publish snapshots, plugin/host lifecycle, project I/O, device setup.
- **Audio thread**: `PlaybackEngine` callback only. It must not touch `Session`, allocate, block, or take locks. It reads **published** immutable views via atomics (see below).
- **Render workers (1.1.18)**: a fixed pool ([`src/engine/InstrumentRenderPool.h`](../src/engine/InstrumentRenderPool.h), owned by `PlaybackEngine`) that renders the **live-instrument generation stage** (MIDI merge + plug-in `processBlock` into the host's own scratch) as one job per host **inside** the callback: the callback dispatches after every MIDI source of the block has been scheduled, participates, and waits for the last job before the row loop applies inserts / fader / pan / meters / routing and sums in the unchanged row order. Jobs never outlive the callback, so every drain / gate written for "the audio thread" (`isAudioCallbackInProcessingSection`, `waitForAudioCallbackExit`, the offline-render gate) still covers the workers. Workers obey the audio-thread rules (no allocation, no locks, no I/O); wake / completion go through `std::atomic::wait / notify` (futex-style), the callback's join spins ≤ 150 µs then blocks. Proxy-backed hosts, the sessionless fallback, the offline mixdown and proxy rendering stay serial. Worker count: `instrument_render::defaultWorkerCount()` (physical cores / 2 − 1, max 7, 0 on ≤ 3 cores) or `--instrument-workers N` (0 = serial, the same code on the callback thread). Report: [`docs/PARALLEL_INSTRUMENT_RENDERING_2026-10-06.md`](PARALLEL_INSTRUMENT_RENDERING_2026-10-06.md).

## App layer: `MainAppWindow.cpp` (`TransportControlsContent`) — composition root

[`MainAppWindow.cpp`](../src/app/MainAppWindow.cpp) defines `mini_daw_app_transport::TransportControlsContent`, the inner transport timeline UI subtree. After modularization (**~988 lines**, down from a much larger monolith), its **intended role** is the **transport UI composition root** — not a dump for feature implementation.

**What it owns / does**

- **Top-level JUCE widgets and views** for the transport strip and timeline chrome (buttons, ruler, lanes, inspector, overlays, MIDI editor component handle, etc.).
- **Construction and member ownership** of **app-layer coordinators**, with **explicit member order** so reverse destruction frees coordinators safely while borrowed UI (`TrackLanesView`, `inspectorView_`, …) remains alive — see destructor-order comments beside `trackLanesEditCoordinator_` and related members.
- **Callback wiring** between coordinators (lambdas in the constructor that forward `transport`, `session`, recorder state, undo entry points, instrument runtime hooks, refresh signals, etc.).
- **Thin shims**: JUCE overrides (`resized`, `changeListenerCallback`, `timerCallback`, clipboard shortcut entry points surfaced through `TransportControlsShortcutTarget`), and **`createTransportUiForMainWindow`** as the factory return type that pairs UI + shortcut target ([`TransportControlsFactory.h`](../src/app/TransportControlsFactory.h)).
- **Legitimate cross-subsystem orchestration** kept local because it stitches multiple-owned UI pieces in one place, for example:
  - **`refreshInstrumentUi()`** — timeline row attachment sync, playback bridge / shell sync with `InstrumentRuntimeCoordinator`, lane header rebuild/repaint, optional MIDI editor refresh, layout.
  - **`syncViewportFromSession()`** — arrangement extent, default samples-per-pixel, viewport clamp tied to ruler width and device sample rate.
  - **`clearExperimentalInstrumentRuntimesPreserveBridgeOnly()`** — resets MIDI editor booking, clears instrument attachments on lanes, clears `InstrumentTimelineRowCoordinator` lanes/headers, then `InstrumentRuntimeCoordinator::clearRuntimesPreserveBridgeOnly()`. **This stays in the composition root** because it crosses MIDI editor + track lanes + instrument timeline rows + runtime cleanup.

**What it must not represent architecturally**

- **Not** where “the feature logic” for recording, project I/O, MIDI editor internals, VST picker flow, lane edit semantics, clipboard rules, undo stack implementation, etc. should accumulate — those belong in the **coordinators and domain modules** below (and callers should stay thin).

**Constructor and size**

- The **constructor is intentionally explicit** — a readable wiring block. Do **not** break it apart only to shorten the file unless a dependency truly changes.
- **~988 lines is acceptable** at the composition layer as long as the file stays **mostly ownership, wiring, and small orchestration**.

**Guidance for changes**

- **Prefer** implementing new behavior inside the **appropriate coordinator** (or a new small module under `src/app/`) and only **threading callbacks** through `TransportControlsContent` when integration requires.
- Keep code here only when it is **composition-root wiring**, **top-level shell behavior** (keyboard focus, splitter, dialogs entry), or **genuine multi-subsystem orchestration** like the helpers above.

**Standalone MainAppWindow refactor**

- Treat **standalone `MainAppWindow.cpp` refactoring as closed**: no further decomposition “for hygiene” unless a **concrete regression** or **feature-driven integration need** proves the split. Resume normal feature work instead.

## Session and snapshot

- **`SessionSnapshot`** is **immutable**. Every session edit builds a new snapshot and publishes it with a single atomic store (`Session::sessionSnapshot_`, `memory_order_release`).
- **`SessionSnapshot::tracks_`** is the **canonical ordered list** of timeline lanes. Row order is what the user sees (headers + lanes) and what undo/redo and project save preserve.
- **`Track::kind`** is `TrackKind::Audio`, `TrackKind::Instrument`, `TrackKind::Midi`, `TrackKind::Group`, or `TrackKind::Master` (Stereo Out). Instrument lanes are **first-class domain rows**, not UI-only decorations. **Midi** rows hold MIDI clips but no plugin and no audio path; they feed an Instrument row via **MIDI To** (see [MIDI tracks](#midi-tracks-and-many-to-one-routing-v18)). Exactly one **Master** row exists per snapshot (final output bus; no timeline clips). **Group** rows are internal summing buses (no timeline clips).
- **`Session::activeTrackId_`** (message-thread only, **not** in the snapshot) selects where **Add clip** targets audio; it does not replace `TrackId` for instrument binding.

**Pointers:** [src/domain/SessionSnapshot.h](../src/domain/SessionSnapshot.h), [src/domain/Track.h](../src/domain/Track.h), [src/domain/Session.h](../src/domain/Session.h), [src/domain/Session.cpp](../src/domain/Session.cpp).

## Multiple instrument tracks (current truth)

- **Multiple `TrackKind::Instrument` rows in one session** are normal, supported architecture — not a transitional exception.
- **`TrackId`** is the stable identity that binds:
  - instrument **runtime** (host + controller maps),
  - **UI** (header, MIDI event lane),
  - **MIDI pattern / editor** binding for that lane,
  - **project** experimental payloads (`experimentalInstrumentTracks[].trackId` for v13+),
  - **playback bridge** entries (`ExperimentalInstrumentPlaybackEntry::trackId`).

Do **not** design new features around a single “the” instrument or “primary” lane unless a future doc explicitly revives that product decision.

## Instrument runtime (TrackId-keyed)

- **Registry** (owned by [`InstrumentRuntimeCoordinator`](../src/app/InstrumentRuntimeCoordinator.h), constructed from `TransportControlsContent` in [src/app/MainAppWindow.cpp](../src/app/MainAppWindow.cpp)):
  - `std::unordered_map<TrackId, std::unique_ptr<ExperimentalInstrumentHost>> instrumentHostsByTrackId_`
  - `std::unordered_map<TrackId, std::unique_ptr<InstrumentTrackController>> instrumentControllersByTrackId_`
- **`ExperimentalInstrumentHost`**: **one instance per instrument track**. Each instance holds **at most one loaded plugin** at a time (`activeOwner_`). Multi-track = **many host objects**, not one host managing many TrackIds internally.
- **`InstrumentTrackController`**: **one per instrument track**; binds that lane’s MIDI clips / render snapshot to the paired host.
- **Staging pair** (`instrumentStagingHost_` / `instrumentStagingController_`): used only around **first-time add / promotion** flows when a runtime is not yet bound to a timeline `TrackId`. It is **not** a second global instrument model alongside the TrackId registry.

## Playback bridge

- **`ExperimentalInstrumentPlaybackSnapshot`** is an immutable list of **`ExperimentalInstrumentPlaybackEntry`** `{ trackId, ExperimentalInstrumentHost*, InstrumentTrackController* }`.
- **Publisher**: message thread calls `PlaybackEngine::publishExperimentalInstrumentPlaybackSnapshot(...)` (`release`-store atomic `shared_ptr`).
- **Consumer**: audio callback `acquire`-loads and retains the `shared_ptr` for the block — same handoff discipline as the session snapshot.
- The callback **walks instrument rows in `SessionSnapshot` track order** and resolves playback entries **by `TrackId`**. Mixed audio/instrument order in the snapshot is intentional; engine logic must handle **every** instrument row — **never** regress to “first instrument only.”

**Pointers:** [src/engine/PlaybackEngine.h](../src/engine/PlaybackEngine.h) (`ExperimentalInstrumentPlaybackEntry`, `ExperimentalInstrumentPlaybackSnapshot`), [src/engine/PlaybackEngine.cpp](../src/engine/PlaybackEngine.cpp).

## Project file (schema v28 today)

- **`ProjectFileV1::kCurrentVersion`** is **28** ([src/io/ProjectFile.h](../src/io/ProjectFile.h)). **v28** adds the optional per-track **`tracks[].colour`** — the track's palette key (`"blue" | "teal" | "green" | "ochre" | "orange" | "red" | "purple"`; see [Arrangement track headers](#arrangement-track-headers-compact-layout-row-height-grid-and-track-colours-2026-10-07)). The key is written only for a non-default colour, so a project without colours is byte-identical to a v27 writer's output apart from the version number; absent key (every pre-v28 file) or an unknown / non-string value reads as the Default grey — never a read failure, and tracks / clips / heights are never altered. The v26 `trackRowHeightPreset` key set grows to `"micro" | "mini" | "small" | "medium" | "large"` (unknown → Medium) and `tracks[].rowHeight` is now clamped only to `[28, 1120]` on load (older on-disk heights such as 64 / 96 / 192 are kept exactly and read as *Custom* until the next resize or preset — nothing is re-snapped on load). **v27** adds the optional root **`visualTrackGroups`** — an array of `{ name, collapsed, memberTrackIds[] }` objects describing the purely visual collapsible track groups (see [Collapsible track groups](#collapsible-track-groups-visual)). The key is omitted when no displayable group exists; only groups that are displayable at save time (≥2 existing members, contiguous in track order) are written, with members filtered to the saved snapshot — stale ids of deleted tracks never reach disk. Member row heights on `tracks[].rowHeight` are always the NORMAL heights: a collapsed group's 4 px display is never written. Absent key (every pre-v27 file) or any malformed shape (unknown ids, overlap, non-contiguous members, <2 members, bogus types) degrades per entry to "no group" — never a read failure, and track/clip data is never altered to repair layout metadata. **v26** adds the optional root **`trackRowHeightPreset`** (`"small" | "medium" | "large"` — the last explicitly chosen shared track-height preset; absent or unknown → Medium) and the optional per-track **`tracks[].rowHeight`** (the row's actual arrangement height in logical px; absent/0 → the preset default; clamped to the valid [Small=64, 480] range by the UI apply). Both are additive UI-only fields with absent-key defaults: every pre-v26 project loads with its historical Medium look, and clip times, routing, Solo memories and musical data are untouched. **v25** adds the optional root **`soloMemories`** — an array of up to four arrays of `TrackId`s (the four persistent Solo memories; omitted when all four are empty, so a project without solo memories is byte-compatible with a v24 reader's expectations). Absent key (every pre-v25 file) or any malformed shape degrades to four empty memories — never a read failure; ids are deduplicated at read time and validated against `tracks` by `Session` on apply (unknown ids never crash and never produce a false-active solo). The temporary solo set, the active memory selection and every derived solo state are deliberately NOT persisted. **v24** adds the optional per-row live MIDI input (`tracks[].midiInput` = `"device"` / `"all"`, `midiInputDeviceId`, `midiInputDeviceName`, `midiInputChannel` 1 … 16; all omitted for None — so no pre-v24 project gains a MIDI coupling by being opened) and the optional `experimentalInstrumentTracks[].clips[].pitchBend[]` points (`startTick`, raw 14-bit `value`, native `channel`; omitted when empty). **v23** adds `tracks[].inputKind` / `inputChanA` / `inputChanB` (audio input assignment), **v22** `tracks[].preGainDb`, **v21** the Secondary instrument object, **v20** `timelineSampleRate` + proxy metadata. **v19** adds optional `experimentalInstrumentTracks[].clips[].ccPoints` — sparse MIDI CC automation points (`startTick`, `controller` 0–127, `value` 0–127, native `channel` 1–16, `interp` = `"hold"`/`"linear"`), omitted when empty; v18-and-older projects contain no key and load with no CC automation and identical sound (see [MIDI CC automation](#midi-cc-automation-stage-d)). **v18** adds `tracks[].kind == "midi"` rows with optional **`midiTo`** (destination Instrument `trackId`; absent = None) and `experimentalInstrumentTracks[].kind == "MidiContent"` payloads for their clips. **v17** adds optional per-track **`midiChannel`** (see [MIDI output channel per track](#midi-output-channel-per-track-v17); absent = `Any`/preserve, which is how every pre-v17 project loads). **v16** adds `experimentalInstrumentTracks[].genericVst3Descriptor`. **v15** adds `tracks[].sends[]`. **v14** adds per-track **`output`** (`trackId` of a Group or Master) and `tracks[].kind` = `"group"` / `"master"`. **v13** introduced mixed `tracks[].kind` + `experimentalInstrumentTracks[].trackId`.
- **`tracks[]`** persists **mixed lane order** and, for v13+, per-row **`kind`** (`"audio"` / `"instrument"` / `"midi"` / `"group"` / `"master"`; absence reads as audio).
- **`experimentalInstrumentTracks[]`** holds Groove/experimental payloads; for v13+ each row binds with **`trackId`** to a timeline instrument lane. For v18, `kind == "MidiContent"` rows bind by id to a `"midi"` timeline row instead (never resolved by name or position).
- **Pre-v13 projects**: `migrateProjectFileExperimentalInstrumentLanePreV13` in [src/io/ProjectFile.cpp](../src/io/ProjectFile.cpp) may **append** an instrument shell track and bind a legacy payload; extra experimental rows beyond the first supported binding can be dropped with a log line.

- **Additive-with-omitted-default is the established migration shape here.** `sends` (v15) and `midiChannel` (v17) both persist only when non-default and read as the legacy-preserving default when absent, so no rewriting migration function is needed. Prefer this over destructive migrations.

### VST3 insert chains in the project file (`tracks[].inserts[]`, v9+)

- **Every row kind that can host inserts is persisted.** `Session::saveProjectToFile` exports `PluginInsertHost::exportChain(trackId)` for **every** `tracks[]` row (Audio, Instrument, Group, Master — the same set the Inspector offers Pre/Post inserts on and the engine processes), and `applyLoadedProjectModel` restores `inserts[]` for every row kind. Until 1.1.7 only Audio rows were exported and `"instrument"` rows were skipped on load, so an insert on an instrument/group/master row silently vanished at save time — the "DAL Mono Delay Post insert did not come back" report. Each row carries `slotId`, `stage` (`"pre"`/`"post"`, chain order = array order), `pluginVst3Path` (locate), `pluginIdentifier` (JUCE identifier string: format-name-pathHash-uid) and `pluginStateBase64` (`AudioPluginInstance::getStateInformation`, i.e. JUCE's VST3 host wrapper blob with component + controller state). Save, Save As and autosave all go through the same call.
- **Unavailable plugins are kept, never erased.** On restore, a row whose plugin cannot be instantiated (bundle missing at the saved path, scan or instantiation failure, or the plugin found at that path is a *different identity* than `pluginIdentifier` — same format + name + uid is the identity test, the path hash may differ for a relocated copy) stays in the live chain as an **unavailable placeholder** (`LiveInsertSlot::unavailableDescriptor`): same slot id / stage / chain position, identity and opaque state untouched, no processor published to the audio thread, listed in the Inspector as `"<name> (unavailable)"`. `exportChain` re-emits it byte-for-byte, so saving while a plugin is temporarily missing preserves its configuration; when the plugin is back the next load applies the preserved state. A saved state is never applied to a plugin of another identity. Only the user's explicit removal (`removeInsert`, undoable, marks dirty) drops a row — the next save then omits it and it does not resurrect on reload.
- **Dirty marking.** Add / remove / move / reorder and editor parameter edits record a plugin undo step through `PluginInsertHost::setUndoRecorder` → `UndoRedoCoordinator::onPluginUndoRecord`, which marks the project dirty.

## MIDI lane and editor

- Per-track **MIDI event lanes** and **instrument header** widgets are owned by [`InstrumentTimelineRowCoordinator`](../src/app/InstrumentTimelineRowCoordinator.h) (private `MidiEventLane` + `TrackHeaderView` maps), embedded in `TrackLanesView`. They close over that lane’s **`TrackId`** (host/controller lookup via `InstrumentRuntimeCoordinator`).
- **MIDI editor orchestration** lives in [`MidiEditorPresenter`](../src/app/MidiEditorPresenter.h); the **window** is [`ExperimentalMidiEditorWindow`](../src/ui/experimental/ExperimentalMidiEditorWindow.h). Opening a clip rebinds so the editor uses the correct host/controller for that track (single window instance, track-scoped binding — not “whichever instrument is global”).

### MIDI timing model, granularity and minimum note length

- **Ticks are the only note time unit.** `TimelineMidiNote::startTick` / `durationTicks` are `std::int64_t` ticks in the clip's own PPQ (`ExperimentalMidiPattern::ticksPerQuarter`, default `kDefaultExperimentalTicksPerQuarter = 960`, saved per clip). Starts and durations share one unit and one granularity: **1 tick is representable everywhere** in storage, editing, project I/O and playback conversion. `durationTicks` is the held length; the overlap end is exclusive (`timelineNoteEndTick = start + max(1, duration)`), so end-to-start touching is legal.
- **Minimum note length is snap-derived, not a fixed constant.** `ExperimentalPianoRollView::minTimelineNoteDurationTicks()` returns the snap grid in ticks when snap is enabled, otherwise `ticksPerQuarter / 16` (**60 ticks = a 64th note** at 960 PPQ). Every editing path funnels through it: create, mouse resize (including multiselect, where the shared delta is clamped so no captured note falls below it), paste, and the typed **Len** field. `validateTimelineNotesNoOverlap` also rejects any candidate below the minimum, so the rule cannot be bypassed by a new caller that forgets to clamp. **Import and project load deliberately clamp only to `max(1, ticks)`**: a foreign file or an older project may legitimately contain shorter notes, and silently lengthening them would alter existing music. So the minimum is an *editing* floor, not a data invariant — code that assumes "every note is ≥ 60 ticks" is wrong.
- **Minimum granularity vs minimum length differ on purpose.** Granularity (1 tick) is what the model can *represent*; the minimum length is what interactive editing is *allowed to produce*. The gap exists because mouse editing at a musical grid should not be able to create notes too short to see, select or hear, while imported material must round-trip unharmed.
- **Snap is global.** One `SnapSettings` on `Session` drives both the arrangement and the MIDI editor (the editor's toggle/combo write straight to the session), so changing snap in one place changes the minimum note length in the other. This is existing intended behaviour, but it is the reason the minimum is not a constant.
- **The `Len` field is exact, not snapped.** Typed lengths use the entered musical value verbatim (subject only to the minimum and to r-unit granularity below); snap constrains *mouse* editing only. Because the minimum is snap-derived, snap still bounds how *short* a typed note may be — with snap at 1/16 the shortest typed length is a sixteenth. Format and conversion live in [`ExperimentalMidiNoteLengthFormat.h`](../src/ui/experimental/ExperimentalMidiNoteLengthFormat.h): `n.p.q.r` = bars . quarters . sixteenths . 120ths-of-a-sixteenth, a mixed-radix number where fields above their base carry (`0.0.0.120` == `0.0.1.0`), display is always normalized, and bar length comes from the project meter (`beatsPerBar`), so odd meters work (a 7/8 bar is 3.5 quarters = 3360 ticks at 960 PPQ). **r has 120 subdivisions** because 120 = 2³·3·5 makes triplets (40 r), quintuplets (24 r) and sextuplets (20 r) of a sixteenth exact whole numbers, which a power-of-two subdivision cannot express. One r unit is `ticksPerQuarter / 480` — **2 ticks at 960 PPQ** — so the field is coarser than storage: a duration that is not a whole number of r units displays rounded to the nearest r while the note keeps its exact ticks, and only a real commit writes the field's value back.
- **Batch note edits are all-or-nothing.** `applyLengthTicksToSelectedNotes` (like paste and multiselect resize) validates the whole candidate batch through `validateTimelineNotesNoOverlap` before writing anything: on conflict nothing changes, no undo step is recorded, and the roll flashes the forbidden cursor. Pairs of selected notes that *already* overlapped in an old project are grandfathered so a legacy clip is not frozen out of editing. Length edits change `durationTicks` only — start, pitch, channel, velocity and off-velocity are untouched — and land as one undo step via `executeUndoableInstrumentEdit`.
- **Known limitation:** MIDI *export* writes a fixed `4/4` time-signature meta event (`InstrumentMidiClipExport.cpp`) regardless of the project meter, so exported files misrepresent bar structure in other meters. The editor itself does not assume 4/4.

### MIDI output channel per track (v17)

- **The channel is a property of the track, not of the note.** `Track::getMidiOutputChannel()` ([src/domain/Track.h](../src/domain/Track.h)) is either `kTrackMidiOutputChannelAny` (**0** — preserve whatever channel each event already carries) or a **fixed 1 … 16** that every outgoing event from that row is remapped to. `sanitizeTrackMidiOutputChannel` repairs anything else. New tracks default to **channel 1**.
- **Why this exists.** Before v17 the MIDI editor stamped **channel 10 on every note it created** (`kCreateNoteChannel`), and the whole pipeline faithfully carried that per-note value through to `juce::MidiMessage::noteOn`. Channel 10 is the General MIDI *drum* convention, so multi-timbral melodic instruments never heard anything: GSi VB3-II listens on channel 1 (Upper), 2 (Lower) and 3 (Pedal), and simply stayed silent. The fix is a per-track channel, not a new hardcoded constant.
- **Remapping happens once, on the message thread.** `InstrumentTrackController::publishRenderSnapshot()` resolves the row's channel and bakes it into every `InstrumentNoteRenderEvent::midiChannel`. The audio thread therefore does no session lookup, and **realtime playback, offline mixdown, the deferred note-off queue (`rtPendingOffs_`) and transport panic all inherit the remap for free** because they consume the same events. `InstrumentTrackRenderSnapshot::midiChannel` is a diagnostic copy only. Changing the channel in the Inspector republishes the snapshot (`refreshMidiOutputChannelFromSession`), so notes already on the timeline move to the new channel; notes *currently sounding* keep the channel they started on, and their queued note-offs carry that same channel, so a mid-note change cannot strand them. All Notes Off already sweeps channels 1 … 16.
- **Drums are chosen explicitly, never inferred.** Only the **Add Instrument Track → Groove Agent SE** creation path selects channel 10 (`kTrackMidiOutputChannelDrums`), because that menu entry *is* the drum instrument. Nothing looks at track or plugin names. New notes created in the editor are stamped with the track's fixed channel when it has one, so stored channel and audible channel agree; on an `Any` row the editor still stamps 10, matching the notes already in migrated projects.
- **Migration is non-destructive.** `ProjectFileV1::kCurrentVersion` is **17**, adding optional `tracks[].midiChannel`. The key is **omitted when the value is `Any`**, and every pre-v17 project loads as `Any` — so old projects keep playing exactly as before (their notes still carry channel 10), multi-channel MIDI imports keep the channel assignment that *is* their musical content, and no note data is ever rewritten. A pre-v17 project re-saved by a v17 writer contains no `midiChannel` key at all. The user can move a migrated row from `Any` to a fixed channel whenever they want.
- **MIDI channel is not audio routing.** The Inspector therefore captions them **`MIDI Channel`** and **`Audio Output`**; neither is called just "Output". `MIDI Channel` is shown on `TrackKind::Instrument` rows only, and commits undoably through `TrackLanesEditCoordinator` like every other routing control. Beware that `Track::channelFaderGain` is a *mixer gain* and has nothing to do with a MIDI channel despite the name.
- **Footgun:** `Track` is rebuilt positionally by ~25 copy-on-write sites in [SessionSnapshot.cpp](../src/domain/SessionSnapshot.cpp) and [SessionRouting.cpp](../src/domain/SessionRouting.cpp). A site that forgets to pass the channel silently resets it to the ctor default of 1 — which is exactly how the first attempt at this slice broke legacy migration. Any new per-track field must be threaded through **all** of them, including the routing/send repair helpers.

### Native vs effective channel: inspection and explicit baking

- **Three separate concepts, deliberately not collapsed.** *Native channel* = `TimelineMidiNote::channel`, stored in the note. *Track output channel* = `Track::getMidiOutputChannel()` (`Any` or fixed 1 … 16). *Effective channel* = what the plugin receives after the track setting is applied. A fixed track channel therefore **hides** whatever native mixture a track contains, and switching back to `Any` reveals it again. All of this is defined once, as pure functions, in [`ExperimentalMidiChannelDiagnostics.h`](../src/ui/experimental/ExperimentalMidiChannelDiagnostics.h) — including the rule for which channel new notes are stamped with (`channelForNewNotes`), so the roll no longer restates it.
- **The mixture is intentional and useful.** One instrument track may hold several native channels; that is how a multi-timbral plugin is driven from a single instance. VB3-II: Upper = 1, Lower = 2, Pedal = 3 — draw each part with the track on the matching fixed channel, then set the track to `Any (Preserve)`. [MIDI tracks](#midi-tracks-and-many-to-one-routing-v18) make this a clearer arrangement model (three lanes, one instrument) without changing these semantics: each MIDI track has its own output-channel setting, applied before its events merge into the destination.
- **The editor reports it, read-only.** A `juce::Label` in the MIDI editor toolbar shows `Native Ch: … · N notes · Output …· Effective Ch: …` for the current selection, refreshed by the same 10 Hz poll as the `Vel` / `Off` / `Len` fields (selection changes from too many gestures to be worth a change callback). The native part is derived from the **note data**, never from the track selector — telling them apart is the entire point. Mixed sets wider than four channels collapse to bare `Mixed` with the full set in the tooltip so the control cannot push the toolbar around. With nothing selected it states only the track's output setting: an empty selection must not display a number the user could read as note data.
- **Baking the channel is explicit, scoped and undoable.** The toolbar's `Ch...` menu offers *Remap Selected Notes to Track Channel* and *Remap All Notes to Track Channel…*. Both require a **fixed** track channel — under `Any` there is no single target, so they are greyed out with the reason in a tooltip — and an empty selection is never read as permission to rewrite the track. Selected scope touches the open clip's selection; all scope iterates `InstrumentTrackController::getClips()`, i.e. **every clip on that track** (not the session). Only `channel` is written: time, duration, pitch, velocity, off-velocity, clip ownership, the selection and the track's own output selector are all left alone, and the notes are deliberately **not re-sorted** so the selection's note indices stay valid across the edit.
- **Remap goes through the normal mutation path**, so it inherits everything: one `executeUndoableInstrumentEdit` step (the musical undo snapshot is already track-wide, which is why an all-clips edit is still a single Undo), `markProjectDirty` → autosave, `notifyClipExperimentalMusicalTimingChanged()` → `publishRenderSnapshot()` for realtime and offline, and plain project I/O for persistence. No audio-thread mutation, locking or allocation is added.
- **Remap can be refused.** Channel is part of note *identity* (`timelineNotesSharePitchAndChannel`), so two overlapping notes on one pitch across different native channels are legal today but would become a single note once merged onto one channel. The batch is validated per clip through `validateTimelineNotesNoOverlap` (originals grandfathered) and refused whole, with an explanation — the same all-or-nothing contract as paste, multiselect resize and the `Len` field. This is a real limitation for stacked legacy material: the user must move or shorten the notes first.
- **In-app help.** `Help → MIDI Channels...` opens a scrollable read-only page ([`MainAppDialogs.cpp`](../src/app/MainAppDialogs.cpp), `midiChannelsHelpBodyText`) covering all of the above, channel 10 as an explicit choice rather than an inference, and legacy projects. It is the one place the wording `Any (Preserve)` is defined; the Inspector dropdown and the editor readout match it deliberately.

### MIDI export and the channel contract

- **Contract (implemented, Stage C):** export under `Any (Preserve)` writes **native** event channels; export under a **fixed** track channel writes the **effective** (remapped) channel — for every channel-voice event (Note On, Note Off, and Stage D CC events). Audio mixdown always uses the effective channel, exactly like realtime playback.
- **How:** [`InstrumentMidiClipExport.h/.cpp`](../src/io/InstrumentMidiClipExport.h) is split into `buildInstrumentMidiClipMidiFile` (in-memory SMF1 builder — the testable seam) and the file-writing `exportInstrumentMidiClipToMidiFile` wrapper; both take `sourceTrackMidiOutputChannel` and apply `midi_channel_diag::effectiveChannel` per event, so exporter and engine share one channel rule. The channel belongs to the **MIDI source track** (the editor passes `ExperimentalPianoRollView::trackMidiOutputChannel()`), never the destination instrument of a routed MIDI-only track. Export builds an output representation only: stored notes, native channels, track settings and CC points are never mutated (asserted by selftests). Meta events (tempo, time signature, track name) are never remapped.
- **Remaining known limitation:** the fixed `4/4` time-signature meta event above (deliberately untouched).

## MIDI tracks and many-to-one routing (v18)

- **`TrackKind::Midi` is a MIDI-only lane**: it owns MIDI clips (same clip model, editor and undo as an instrument lane) but has **no plugin, no host, no audio path** — no audio output routing, sends, or inserts. It contributes to the mix only by feeding an Instrument row.
- **MIDI To** (`Track::getMidiDestinationTrackId()`): identity-based (`TrackId`), `kInvalidTrackId` = None/disconnected. Legal destinations are existing `TrackKind::Instrument` rows only; `Session::setTrackMidiDestination` and load-time repair (`session_routing::repairMidiDestinationsInPlace`) enforce this — a stale id is repaired to None, never retargeted. **Many-to-one is the point**: several MIDI tracks may feed one instrument (each with its own [output channel](#midi-output-channel-per-track-v17) baked in before the merge); one MIDI track feeds at most one instrument.
- **Runtime**: a plugin-less **MIDI content controller** — an `InstrumentTrackController` constructed with a **null host** — keyed in `InstrumentRuntimeCoordinator::midiContentControllersByTrackId_`, separate from instrument runtimes. It is never a playback-bridge *instrument* entry; instead the bridge snapshot carries it in **`ExperimentalInstrumentPlaybackSnapshot::midiSources`** (`{trackId, controller}`, published in session track order).
- **Engine merge (audio thread, [PlaybackEngine.cpp](../src/engine/PlaybackEngine.cpp))**: each block, after every instrument entry schedules its own lane's events, MIDI sources are walked **in snapshot order** (deterministic merge order). Each source resolves its destination **per block** from the *current* session snapshot (`findTrackIndexById` → `getMidiDestinationTrackId`) and schedules its transport MIDI into the destination's host. Unresolvable destination = silent. No graph solving, allocation, or locking is added.
- **Note lifecycle**: sounding notes belong to the **source** controller (its pending note-off queue), not the destination. A **reroute** mid-playback first flushes that source's pending note-offs into the **old** destination's host (never `allNotesOff` — the destination may sustain other sources), then routes new events to the new destination. **Stop** flushes all MIDI sources' pending offs into their last-routed destinations before the per-instrument transport flush. **Delete** of either end goes through the same snapshot/registry republish protocol as instrument runtimes (publish-before-destroy, drain in-flight callback).
- **Offline mixdown** runs the identical destination resolution and merge order, so a bounce renders routed MIDI exactly like realtime.
- **UI**: the add-track menu has **Add MIDI Track**; the Inspector shows **MIDI To** (Instrument rows + "No destination") and **MIDI Channel** for Midi rows, and hides audio output routing. Opening the MIDI editor on a Midi-track clip resolves the *destination's* host for preview/readouts; with no destination set, an alert explains instead. Rerouting or deleting the destination while the editor is open on that track rebinds/closes it (`resetMidiEditorBookingIfOpenOnTrack`).
- **Persistence (v18)**: `tracks[].kind == "midi"` + optional `midiTo` (absent = None); clips persist as `experimentalInstrumentTracks[]` rows with `kind == "MidiContent"`, bound strictly by `trackId` on load. Additive-with-omitted-default, like v15/v17 — pre-v18 projects contain neither key and load unchanged.
- **Deterministic test seam**: `ExperimentalInstrumentHost::MidiDeliveryCaptureSink` (install via `installMidiDeliveryCaptureSinkForTests`) observes the exact merged `juce::MidiBuffer` at the host's processing boundary — with a sink installed the boundary runs **without any loaded plugin**, so routing is testable without a VST3. The **`--stability-midi-routing`** scenario ([StabilityScenarioRunner](../src/diagnostics/StabilityScenarioRunner.h)) builds the headline **many-to-one** fixture on a copy of the given project: one instrument destination with its **own** clip on channel 1 plus two routed MIDI sources ("Lower" fixed output channel 2 / native 5, "Pedal" fixed 3 / native 6, pitches including the range boundaries 0 and 127). It asserts **exact per-channel note-on counts** (channels 1/2/3 stay distinct, mask `0x07`), that the destination's processing boundary ran **once per block, not once per source** (sink block count vs `getMidiDeliveryBoundaryBlockCountRelaxed`), that stop flushes all note-offs, then runs an **offline mixdown parity pass** over the same capture assertions, and finally verifies the v18 save/reload roundtrip preserves both destinations, fixed output channels, native channels and exact stored pitches. **Stage D extends the fixture with CC11 automation** (destination's own clip, native channel 1; the "Lower" source stored on native channel 5) and asserts exact per-channel CC deliveries (`2/2/0` — effective channels, no repeat-flood, no leak onto the CC-free source's channel), that a CC never arrives **after** a Note On at the same sample offset **on its own channel** (the sink counts only channel-voice controllers < 120 — the stop flush legitimately sends All Notes Off/CC 123 on every channel), and the same CC assertions on the offline pass (realtime/offline CC parity).

## MIDI editor UX: title, destination status, full range and audition (Phase B.1)

- **Window title is generic and live**: `MIDI Editor — <track name>` built by [`MidiEditorTitleStatus.h`](../src/ui/experimental/MidiEditorTitleStatus.h) (pure, testable text builders; no internal labels like "I2", no legacy "(Drum hits)", no row-mode description). `MidiEditorPresenter` resolves the name by `TrackId` at bind time and installs a **title provider** the window's UI timer polls, so a track rename updates the open editor without a rebind.
- **The status line is destination-aware**: instrument tracks show their own plugin (`Instrument: VB3-II` / `No instrument loaded`); MIDI tracks never claim a plugin they must not own — they show `MIDI To: <dest> — <plugin>`, `No MIDI destination`, or `<dest>: No instrument loaded`. Resolution is `TrackId`-backed on the message thread (`resolveBoundTrackStatus` in [`ExperimentalMidiEditorWindow.cpp`](../src/ui/experimental/ExperimentalMidiEditorWindow.cpp)), refreshed by the existing UI poll so destination change/rename/plugin load all update live.
- **Full MIDI range**: all row modes cover pitches **0–127** (`kFullPitchLow`/`kFullPitchHigh` in [`ExperimentalPianoRollView.h`](../src/ui/experimental/ExperimentalPianoRollView.h)); Piano vs Drum is display only. Labels use JUCE's Cubase-compatible octave naming (MIDI 0 = C-2, 60 = C3, 127 = G8). The old per-kind clamps (~C0–C4) are gone from creation, dragging, hit-testing and audition alike; stored pitches are never rewritten (non-destructive — proven by the roundtrip assertions above). An editor without preserved view state seeds its vertical scroll to reveal existing notes, else centers around middle C (`seedDefaultVerticalScroll`).
- **Audition is destination-aware and gesture-scoped** ([`MidiEditorAuditionModel.h`](../src/ui/experimental/MidiEditorAuditionModel.h) — a pure scheduler with a fake-clock seam, driven by [`ExperimentalMidiPatternPlayer`](../src/ui/experimental/ExperimentalMidiPatternPlayer.h) via the same `enqueueMidiMessageFromMessageThread` path as everything else; MIDI tracks audition through their **MIDI To** destination host, never a plugin call from the GUI thread). Channel choice mirrors playback: `Any (Preserve)` uses the note's native channel, a fixed track channel uses the effective channel; key-strip/drum-row audition uses the channel a newly created note would get, then applies the track output semantics.
- **Two deliberate timing semantics**: clicking an **arranged note** is event audition — Note On at Mouse Down, Note Off at `max(default ≈ 850 ms, hold duration)` (`kArrangedAuditionMs`), never the arranged length. The **left piano keys and drum rows** are a manual test instrument — Note On/Off exactly on Mouse Down/Up with no minimum, using the editor's current `Vel`/`Off` values.
- **Ownership and cleanup**: each active preview is keyed by (channel, pitch) with its Note On-time channel captured for the matching Note Off; retriggering restarts the attack without letting a stale scheduled off cut the newer preview, and completion is per-note (no broad All Notes Off). Editor close and player rebuild release everything; window focus loss releases held gestures while quick-click tails still end via their scheduled off. Reroute/channel changes go through the existing Phase B source-specific flush.
- **Live gesture wiring (regression-hardened)**: `ExperimentalPianoRollView::mouseUp` ends the active audition gesture **first, before any early return** — this is the call that schedules the arranged-note Note Off (max rule) and releases key/drum previews exactly at Mouse Up. Its absence was a real shipped regression (previews stayed "held" forever; only focus-loss cleanup released them), so the player now also has a deterministic **integration seam**: `ExperimentalMidiPatternPlayer::TestSeams` (injected clock + MIDI-capture delivery boundary) lets `MiniDAWSelftests` drive the *real* player scheduling/dispatch and assert the actual dispatched `juce::MidiMessage`s. The production host binding (`enqueueMidiMessageFromMessageThread` + `hasInstrument`) lives in [`ExperimentalMidiPatternPlayerHostBinding.cpp`](../src/ui/experimental/ExperimentalMidiPatternPlayerHostBinding.cpp) (app target only) so the player TU links into the selftests without the plugin host.
- **Level-1 selftests**: `MiniDAWSelftests` (console target, [tests/selftest/MiniDAWSelftestsMain.cpp](../tests/selftest/MiniDAWSelftestsMain.cpp)) covers the title/status wording, octave labels 0–127, channel semantics, the full audition scheduler timing/cleanup matrix against a fake clock, and the audition **dispatch integration** matrix (quick click, >850 ms hold, key/drum exact lifetime, channel pairing, teardown/reroute release, retrigger isolation, no duplicate cleanup, independent simultaneous previews, CC-before-Note-On) — no audio device, UI or plugin.

## MIDI CC automation (Stage D)

- **Model, pure and clip-owned.** [`ExperimentalMidiCcAutomation.h`](../src/ui/experimental/ExperimentalMidiCcAutomation.h) defines `MidiCcPoint { startTick, controller 0–127, value 0–127, native channel 1–16, interpolationToNext = Hold | Linear }` and every rule as pure functions: `normalizePoints` (clamp, drop negative ticks, canonical sort, duplicate identity at the same controller/channel/tick resolved deterministically — **last wins**), `valueAtTick` (exact endpoints; Hold retains; Linear interpolates with round-half-up; **no value before a stream's first point** — no invented default like 0/64/127; the final point holds forever), and `collectCcEventsInTickRange` (the bounded discrete event set: a monotonic linear segment emits at most one event per crossed integer value, endpoints exact; an optional `lastSentValue` chase parameter suppresses unchanged repeats). Points live on `ExperimentalMidiPattern::ccPoints`, i.e. **inside the clip**, so move/duplicate/delete/cross-track-move of a clip carries its controller performance with zero extra lifecycle code, and the musical undo snapshot (which serializes whole clips) includes CC state automatically (`experimentalInstrumentClipMusicalEqual` compares it, so CC-only edits create undo steps).
- **Channel semantics are the note rules, verbatim.** Stored points keep a **native** channel; delivery and export apply the source track's `Any (Preserve)`/fixed setting through the same `midi_channel_diag::effectiveChannel` helper as notes. New points are stamped like new notes (`channelForNewNotes`). MIDI-only tracks route CC through **MIDI To**; the destination's own channel setting is never consulted for a routed source.
- **Realtime.** `InstrumentTrackController::publishRenderSnapshot` bakes points into per-`(controller, effective channel)` **`InstrumentCcRenderStream`s** of sample-positioned events (message thread). On the audio thread `audioThread_scheduleCcForSegment` runs **before** note scheduling each segment, so a CC at a note's start enters the `juce::MidiBuffer` (stable insertion order at equal offsets) ahead of that Note On; multiple sources merge in the established deterministic routing order (last deterministic event wins on conflicts). Per-stream `rtCcLastSentValue_` dedups repeats (no floods); it is forgotten on stop/reroute-flush and on snapshot revision bumps, forcing a fresh **chase**: at any discontinuity (playback start, seek, restart, loop wrap, offline render start) the latest event strictly before the segment start — which equals the evaluated curve value there — is emitted at the segment's first sample. Controllers are sticky: no reset value is ever sent on stop, mute or reroute, because none exists generically. Offline mixdown consumes the same snapshots (realtime/offline parity is asserted by the routing scenario).
- **Editor lane.** A collapsible controller lane sits below the velocity lane in [`ExperimentalPianoRollView`](../src/ui/experimental/ExperimentalPianoRollView.h) (collapsed by default with a labeled `CC` restore knob; resize band on its top edge). Header click opens the controller selector (controllers present in the clip first, then the named common set — CC1/2/4/7/10/11/64/65/66/67/91/93 — then all 128 grouped; **CC11 Expression is the default first view**). Rendering: 0–127 vertical range, points, linear ramps vs hold steps, held tail after the final point, distinct accent colour from velocity bars. Editing: click-empty inserts (snap-floor, value from height), drag moves in time (snap) and value, Shift extends selection, right-click = delete / Hold / Linear, Delete key removes selected points (checked **before** the note shortcut). All edits commit as single undoable steps through the same `undoablePatternEditHandler_` gateway as note edits (dirty/autosave inherited); live drags mutate the pattern and rewind before the undoable commit, exactly like velocity drags.
- **Audition.** Clicking an arranged note first evaluates every CC stream of the clip at that note's tick and enqueues the chased values (effective channels) via `ExperimentalMidiPatternPlayer::sendControllerChangeNow`, **then** begins the preview — the host's message-thread MIDI queue is FIFO, so CC precedes the audition Note On. The left piano keys remain a plain manual test instrument (Phase B.1 semantics untouched; no CC is implied there).
- **Export.** The Stage C builder emits CC automation as standard Control Change events (deterministic bounded ramps, exact endpoints, effective channels, added before notes so equal-tick CC precede Note Ons after the stable sort). `InstrumentMidiClipExportResult::ccEventsExported` reports the count.
- **Selftests.** `MiniDAWSelftests` covers validation/boundaries/duplicates, Hold/Linear/endpoint/before-first/after-final evaluation, bounded deterministic ramp generation, no-flood rescans, export CC correctness (channels/ticks/ordering/non-mutation), v19 round-trip and v18→v19 migration (`ProjectFile.cpp` is compiled into the selftest target). The `--stability-midi-routing` scenario asserts realtime + offline CC delivery and ordering at the capture seam.
- **Out of scope by design:** velocity→CC conversion, VST parameter automation, MPE, NRPN/RPN, SysEx editing, Bezier curves, external MIDI output.

**Pointers:** [src/ui/experimental/ExperimentalMidiCcAutomation.h](../src/ui/experimental/ExperimentalMidiCcAutomation.h), [src/instruments/InstrumentTrackController.h](../src/instruments/InstrumentTrackController.h), [src/io/InstrumentMidiClipExport.h](../src/io/InstrumentMidiClipExport.h), [src/ui/experimental/ExperimentalPianoRollView.h](../src/ui/experimental/ExperimentalPianoRollView.h).

## Level meters, export level report and the Inspector channel panel

- **Realtime-safe accumulators, UI drains.** [`engine/LevelMeterAccumulator.h`](../src/engine/LevelMeterAccumulator.h): the audio thread folds every rendered block into relaxed atomics — per-channel sample-peak hold (CAS max), count of samples with |x| > 1.0 ("overs"), sum of squares (RMS), plain sum (DC offset), block / sample / non-finite counters. The message thread drains-and-resets at its own rate, so a peak between two UI reads is never lost. No locks, allocation, logging or UI on the callback. `PlaybackEngine` owns exactly two: the **Stereo Out** accumulator (folded on every callback return path from the final device output, channels 0/1 — the last float signal before the driver converts it; silence while an export gates the callback) and **one metered track** accumulator (`setMeteredTrackForUi`; the audio thread compares the row id against a relaxed atomic at each post-strip stage: audio clip segments, the live-input monitoring pass, instrument host output, group bus strip). The track point is *after* pre-gain, inserts, fader / mute and pan and *before* the output bus and sends, so it measures the actually active source (clip path, Monitor input, Primary / proxy / Secondary audition) with the real mute / routing logic. Master rows are never double-metered: their meter is the Stereo Out meter.
- **Export level report.** `exportStereoMixdownWavBlocking` (and therefore the MP3 pipeline) folds every rendered float block — the same Stereo Out point, before the writer converts it — into `MixdownExportLevelReport` (peak, overs, RMS, DC offset, NaN/Inf, first/last samples) returned through `MixdownExportRequest::levelReportOut` and logged to `mixdown-diag.log`. The completion alert shows the peaks and explicit **OVERLOAD** (mix exceeded 0 dBFS: a PCM WAV is hard-clipped there by JUCE's writer, an MP3 overshoots on decode) and **DC OFFSET** (a plug-in emits a constant offset: wasted headroom, clicks at file edges) lines, so a transient overload stays visible after the animated meter fell. DAL deliberately adds **no** normalisation, limiter, DC filter or fades to the render — it shows the problem; the user fixes the mix. Realtime callback and offline render are sample-identical for deterministic content (`ExportLevelFocusedTests`), so the exported level *is* the realtime Stereo Out level.
- **Concurrent per-row meters — `TrackMeterBank` + `LevelMeterHub` (1.1.16).** The single metered-row accumulator above stays for diagnostics (`setMeteredTrackForUi` / `drain*ForDiagnostics`, used by the `--stability-*` scenarios); the UI no longer drains the engine directly. [`engine/TrackMeterBank.h`](../src/engine/TrackMeterBank.h) holds `kMaxSlots` (256) `level_meter::Accumulator` slots and a published immutable **slot map** (TrackId per slot, acquire-loaded once per callback in `audioThread_beginBlock`); the four existing post-strip fold points call `audioThread_foldTrackMeterIfMetered`, which computes the block statistics once and folds them into the single-row accumulators and / or the row's slot. `PlaybackEngine::setConcurrentlyMeteredTracks(ids)` (message thread) keeps the slots of rows that stay, frees the rest and assigns reset slots round-robin to new rows (a block in flight under the previous map can at worst colour one 33 ms window); `drainConcurrentTrackLevels(id)` drains one row. The Master row is never in the bank — its level is the Stereo Out accumulator. [`ui/LevelMeterHub.h`](../src/ui/LevelMeterHub.h) (owned by `TransportControlsContent`, declared before the views) is the **only drainer**: at 30 Hz it asks its `Listener`s which rows they display (`collectMeterInterest` — hidden views report nothing), publishes the union to the engine, drains each row once plus the Stereo Out window, and hands every window to every listener (`meterWindowArrived`; the master window under the Master row's id), then ticks their animations. `ChannelStripPanel` and every `MixerChannelStrip` are listeners, so the Inspector and the mixer show the same row with identical peaks and no window is ever consumed twice or lost; the overload lamp's click is forwarded as `acknowledgeOverload(id)` to every view (`LevelMeterComponent::resetOverloadLatch(notifyOwner=false)` on the receiving side, so the acknowledgement never echoes). With the mixer hidden only the Inspector's row is metered.
- **Inspector column = scroll area + fixed channel panel.** [`InspectorPanel`](../src/ui/InspectorPanel.h) owns the former `InspectorView` inside a vertical `juce::Viewport` (the view reports `getPreferredContentHeight()` from its own layout pass) and a bottom-pinned [`ChannelStripPanel`](../src/ui/ChannelStripPanel.h) (preferred 210 px, minimum 150 px; on low windows the scroll area keeps ≥ 160 px before the panel shrinks). `TransportControlsContent` keeps an `InspectorView&` into the panel so existing call sites are unchanged; the Inspector default width is 160 px (collapsible / resizable as before). The panel shows the active row's name, its **existing Channel Volume** as a vertical fader ([`ChannelFaderComponent`](../src/ui/ChannelFaderComponent.h) → `Session::setTrackChannelFaderGain`, the same direct setter and no-undo policy the removed text field used; graded −∞ … +6 dB travel from [`ChannelFaderScale.h`](../src/ui/ChannelFaderScale.h), value field, Ctrl/Cmd+click = 0 dB, wheel ±0.5 dB) and **exactly one output meter: the selected row's own audio output** ([`LevelMeterComponent`](../src/ui/LevelMeterComponent.h): 0 … −60 dBFS, L/R bars or one bar for mono, time-based fall 24 dB/s independent of repaint rate, 2 s peak hold, numeric held peak never capped at 0 dBFS, sticky overload lamp reset by click, "DC" tag above −40 dBFS that drops when no block has been folded for 0.5 s). Audio / instrument / group row: that row's fader + its post-strip meter (caption "Out"). Stereo Out row: the master fader + the Stereo Out meter (caption "Stereo Out", fed from the master accumulator — the master is never double-metered). **MIDI row or no selected row: the panel is hidden** (`ChannelStripPanel::hasAudioStrip()` false → `InspectorPanel` gives the whole column to the scroll area; `onAudioStripVisibilityChanged` re-lays out on row switches). There is no always-visible master meter since 1.1.9 (the 1.1.8 instruction for one was explicitly replaced); the master accumulator keeps folding regardless, so export diagnostics and `--stability-*` measurements (`drainMasterOutputLevelsForDiagnostics`) work with any row selected. Track switch, delete and project replace change the panel's meter interest (hub) and clear the UI meter. Fader dB = gain; meter dBFS = signal level; sample peak is labelled as such (not true peak). Track headers are untouched; the mixer window (1.1.16) shows the same fader + meter per row through the same hub.

## Live MIDI input, monitoring and recording

Full report with the time model, behaviour matrix and verification: [`LIVE_MIDI_RECORDING_2026-10-03.md`](LIVE_MIDI_RECORDING_2026-10-03.md).

- **Configuration lives in the session, flags are runtime.** `Track::getMidiInputAssignment()` (`TrackMidiInputAssignment`: `None` / `Device` (JUCE device identifier + readable name) / `AllEnabled`, plus an `Input Channel` **filter** 0 = all / 1 … 16) is set undoably from the Inspector (`Session::setTrackMidiInputAssignment`, Instrument and Midi rows only) and persisted in **v24**. The filter never rewrites a received channel; the row's `MIDI Channel` (Preserve / Force) is applied on delivery exactly as for playback, and the Secondary's forced mapping stays at the host boundary. A missing device stays assigned and is shown as "(missing)" — never replaced by another device. **Monitor** and **Record-arm** of Instrument / Midi rows are runtime-only sets in [`LiveMidiInputCoordinator`](../src/app/LiveMidiInputCoordinator.h) (both OFF when a project opens; independent of each other and of row selection). Audio rows keep their own audio Monitor / `RecorderService` arm.
- **Realtime core: [`engine/LiveMidiInputBus`](../src/engine/LiveMidiInputBus.h).** One preallocated SPSC ring per device slot (producer = that device's JUCE MIDI thread via a per-slot `MidiInputCallback` that does nothing else; consumer = the audio callback). The callback acquire-loads the published **routing snapshot** (rows × device slot × channel filter × monitor × capture) each block — same discipline as the session and instrument snapshots — and, after the hosts' `audioThread_beginAudioBlock` and before processing, delivers monitored events into the destination host resolved like transport MIDI (Instrument row → itself, Midi row → `MIDI To`, re-read from the session snapshot every block) through `audioThread_addMidiEventForCurrentBlock` with a **sample offset** (events received in `(previousCallback, now]` spread proportionally over the block). **Live-note ownership**: each delivered Note On is remembered with host + effective channel so the Note Off reaches the same place after any setting change, and Monitor off / input or routing change / device loss / track removal release exactly that row's notes (targeted Note Offs — never a global All Notes Off). Overflow of a device ring drops + counts, releases that device's notes and marks the take. The offline-export gate, suspended instrument processing and device start discard pending input; live MIDI never reaches `renderOfflineMixdownBlock`. No allocation, lock, logging or host dereference on the audio thread.
- **Recording** reuses `RecordingCoordinator`: armed, configured MIDI rows join the armed audio track in ONE take with ONE boundary (the playhead when the count-in ends; stop boundary = the stop playhead). The bus stamps every captured event with its transport-timeline position (`playheadAtBlockStart − (now − t)·sr − reported output latency` — the moment the key was pressed, not the drain time; see the report for the model) and a playing flag; the coordinator drains the capture ring at 30 Hz into an always-on per-row state tracker (held keys, controller / wheel state) and, during a take, into the take's event list. [`LiveMidiTakeBuilder.h`](../src/app/LiveMidiTakeBuilder.h) (pure) turns that into one clip pattern per row in the **project tempo / PPQ**: velocity 0 = Note Off, keys held across the start enter at tick 0, known sustain / expression / modulation / volume / pedal controllers and pitch bend are restated at tick 0, keys held at Stop end on the stop boundary and a held sustain is released there, recorded CC points are `Hold` (nothing interpolated), an empty take yields no clip and no undo step, a controller-only take is content. `InstrumentTrackController::appendRecordedTimelineMidiClip` places the clip with the take as its window. The whole commit (audio take + MIDI clips) is ONE undo step via `UndoRedoCoordinator::executeUndoableRecordingCommit`. Project replacement aborts a running MIDI take without clips.
- **One record run, one stop boundary (1.1.13).** `PlaybackEngine` owns a *record run* handshake (`RecordRunState` Idle → StartRequested → Running → StopRequested → Stopped; `requestRecordRunStart/Stop`, `waitForRecordRunStop`, `finishRecordRun`). The audio callback stamps a `RecordRunBoundary {monoSample, timelineSample, wrapSerial}` at the **first sample of the block** in which it acknowledges the start and the stop — before it loads the transport intent — and pushes recorder input only while Running. `RecordingCoordinator` writes the Stopped intent, requests the run stop and waits (≤ 250 ms) for the acknowledgement; that single boundary (`RecordRunBoundaries`, logged as `[Rec] run boundaries`) is what every finalization reads: audio frames = stop.mono − start.mono, MIDI take end = (stop.timeline, stop.wrapSerial) with the bus's wrap markers cut at stop.mono, Cycle passes = stopWrap − startWrap, linear audio placement = start.timeline + the latency-store offset. The deliberate audio / MIDI placement compensations stay separate from the raw boundary (`recordingPlacementOffsetSamples` vs the MIDI gesture offset). No callback within the wait (device stopped / lost) ⇒ a message-thread fallback boundary flagged `acknowledgedByEngine=false`, the take is still finalized, and `FinishRunAtExit` guarantees the recorder has stopped using its FIFO before anything is freed. UI reads of the playhead are no longer a finalization input.
- **Arrangement extent grows on demand (1.1.13; replaces the 30-minute reserve).** While a run captures (`recordRunCapturing`, true for MIDI-only takes too — `recorder_->isRecording()` alone is not), the engine's run-end rule uses `timelineEnd = max(extent, t0 + block)`, so the transport never freezes at the old end and no engine correctness depends on a UI timer; a 10 Hz message-thread timer (`RecordingExtentFollowTimer`) grows the stored extent to playhead + 5 s for the navigation area (grow-only `Session::setArrangementExtentSamples`). At Stop `Session::restoreArrangementExtentAfterRecording(storedBefore, resultEnd)` leaves max(extent before the run, derived timeline length, end of the result): the previous extent plus what the result needs, no reserve. Cycle runs do not lengthen the project beyond the loop end; saved extents are never shrunk; playback keeps its own end rule; locators and export range are untouched.
- **Cycle recording (1.1.12) — one take per pass, engine-delimited.** The time base is the engine's **monotone device clock** (`PlaybackEngine::monoSampleClock_`, advanced every callback on every path, `BlockContext::monoSampleAtBlockStart`). The bus keeps **timeline anchors** (one per discontinuity of the mono→timeline mapping: play start, seek, wrap, stop — recorded by the audio thread from the engine's own block segments; `audioThread_noteCycleWrap` is called in both wrap branches with the exact in-block wrap sample) and maps every gesture mono→timeline through them, so an event delivered a block after the wrap still lands before the right locator in the previous pass. Each wrap also pushes a **wrap marker** (`CapturedEvent::wrapMarker`: mono sample, loop start, transport wrap serial) into the capture ring — passes exist even when no MIDI arrives; nothing is derived from a UI timer or from event order. At Stop the coordinator reads `(stopSample, wrapSerial)` as a consistent pair; `live_midi_take::buildTakePasses` keeps the markers with `serial <= stopWrapSerial`, discards everything on the mono clock after the first later marker, assigns each event to the pass whose markers precede it on the mono clock, and builds the windows `[record start, R)`, `[L, R)` …, `[L, stop)` (a stop exactly on a wrap yields no zero-length pass; linear recording = one window). Each pass runs the single-window builder from the row state at the end of the previous pass: a key held across a wrap ends on the previous pass's end and re-enters the next pass at tick 0 with its channel and velocity, sustain / expression / wheel state is restated at tick 0, a held pedal is released on the pass end; these synthesized boundary events exist only in the stored takes (the live tracker never sees them). With Cycle, **every pass of positive length becomes a clip, silent or controller-only too** (it masks earlier material like an audio pass); with Cycle off an empty take still yields no clip. Passes are appended oldest first, so the latest pass is the topmost layer; the audio cycle slices of a combined take count wraps from the same `stopWrapSerial` and the whole run — all audio slices + all MIDI passes of every row — is ONE undo step (older takes are never overwritten). The count-in runs once, before the run.
- **While a row records, its own earlier takes are silent.** `LiveMidiInputCoordinator::beginTake` sets `InstrumentTrackController::setTransportClipsSuppressedForRecording(true)` on every recording row (cleared at commit / abort / project replace); the scheduler then flushes pending note-offs and schedules nothing from that row's clips, so the live performance is never doubled by the previous take. Monitor still decides live audibility, R alone (not recording) never silences clips, other rows into the same instrument keep playing, and the take preview is drawn only. Limitation: a destination playing a **proxy** with Monitor off still renders its earlier takes from the WAV (a proxy cannot mute one row); with Monitor on the live-source policy applies as before.
- **Pitch bend is now part of the clip model.** `ExperimentalMidiPattern::pitchBendPoints` (`MidiPitchBendPoint`: raw 14-bit, native channel, hold semantics, normalized last-wins like CC) flows through the render snapshot (`InstrumentPitchBendRenderStream`, chased and deduplicated like CC on realtime and offline paths), the proxy snapshot / fingerprint (section written only when present, so existing generations stay Current) / offline sequencer, project v24, musical undo equality and the SMF export (Pitch Wheel events, same channel contract). There is no editor lane for it in this slice.
- **Primary / proxy / Secondary while monitoring or recording.** `ProxyPlaybackCoordinator::Dependencies` carry two independent *live-rendering needs*: `liveMonitorRequested` (any monitored row with a configured input whose destination is this row) and, since 1.1.13, `liveRecordingRequested` (a MIDI take — count-in included — runs on a source row into this row: `LiveMidiInputCoordinator::liveRecordingRequestedForDestination`, fed by the take rows or the pending rows set through `setTakePending`). Either need makes a `useProxy` decision fall through to **SecondaryLive** when a Secondary can be loaded — the Secondary becomes the transport source temporarily for the existing clips *and* the live input (one instance; never proxy + live together; other source rows into the destination keep sounding there while the recording row's own clips are suppressed). The evaluation reports both flags (`liveMonitorOverride`, `liveRecordingOverride`; `isLiveMonitorOverrideActive` / `isLiveRecordingOverrideActive` / `isPlayingProxy` drive the Inspector's status: "Secondary instrument used temporarily while recording", "… (Monitor on, recording)", "Monitoring through the Secondary instrument (temporary …)"). Arming alone creates no need. Monitor and Record never touch generation currency, identity, plugin state or the dirty flag by themselves; when the last need ends (Monitor off, Stop, abort, start failure, routing change) the normal policy is re-evaluated against the real fingerprint — a committed take is a musical edit and makes the generation Stale honestly, an undone one leaves it Current (the Secondary gets the existing all-notes-off on deactivation). Without a usable Secondary the proxy keeps playing as backing, MIDI is still captured and the status says "Recording: earlier material on this track is still heard from the proxy - no live instrument is available"; with neither Primary nor Secondary nor proxy, the status says live MIDI is recorded but not heard. Loading happens on the message thread through `ensureSecondaryInstrumentLoadedForTrack`; nothing queues live notes for a plug-in that is not ready. The diagnostics registry (`exportKeyedRuntimePointersForDiagnostics`) reports the row's *transport* host, so the playback-bridge invariant holds while the Secondary is active.
- **UI.** Inspector `MIDI Input` / `Input Channel` + a status line for real obstacles only (R / Monitor on without an input, device missing, device could not be opened, All without a connected device, no playable instrument, Secondary temporary, proxy still heard while recording, overflow) — a working input shows nothing and the status area collapses; the per-route event counters stay internal (the "MIDI received: N events" text was removed in 1.1.13; incoming MIDI is the header's activity dot); header Monitor (speaker) and R cells are live on Instrument **and** Midi rows (the Midi row strip is `[Power][Mute][Monitor][Arm]`, 4 cells, inside the 132 px minimum) and — like Mute / Power and the audio rows' cells — **activate the row** so the Inspector edits the row whose buttons were pressed (1.1.11; the 1.1.10 cells did not, and a MIDI Input picked right after clicking R landed on the previously active track); a MIDI Input pick refreshes the coordinator's devices + routing immediately. ## MIDI clip layering (one overlap rule for audio and MIDI)

- **The rule.** On one source track (an Instrument row's own clips, or a `TrackKind::Midi` row's clips) the MIDI clips form a **layer stack in stored order** (`InstrumentTrackController::clips_`; index 0 = bottom, last = topmost). The topmost clip owns its whole window `[start, end)` — rests and completely empty clips included — and a clip underneath is heard only outside the windows of the clips above it. This is the same model the audio lanes use (`Track` placed clips, front-most wins), expressed in the MIDI clip stack's own direction. A new recorded take and a paste are appended (topmost); delete / save / load / musical undo round-trip the order positionally; a moved clip that ends up free of overlap is promoted to the top (the audio lanes' committed-move rule in `SessionSnapshot::withClipMoved`), a move that still overlaps keeps its layer; selection, focus and the MIDI editor never reorder the stack; cross-track moves append on the target. The lane paints bottom→top and hit-tests top→bottom from the same vector. The selection is **per source track**: the instrument's own Upper clips and each routed Lower / Pedal row are layered independently and still sound together through one instrument; sources sharing a MIDI channel keep the deterministic session-order merge (no channel isolation is claimed).
- **Bake, shared by both render paths** ([`instruments/MidiLayeredRenderBake.h`](../src/instruments/MidiLayeredRenderBake.h), pure): `audibleSpansPerClip` (window minus the windows above), `forEachAudibleNoteSegment` and `restrictStreamToAudibleSpans`. `InstrumentTrackController::publishRenderSnapshot` and `proxy_render::ProxyOfflineSequencer::bakeUnit` both use it line for line, so realtime playback, offline WAV / MP3 mixdown (which drives the live scheduler) and proxy rendering select the same events. **Notes** are cut into one segment per audible span; a segment that starts later than the note is a new Note On with the note's channel and velocity (the attack restarts — accepted); every segment ends at its span end or the note end; the snapshot carries ONE merged, pre-segmented note list per track (`InstrumentTrackRenderSnapshot::notes`, ascending sample, stack order then stored order for equal samples) that the scheduler walks — so a segment ending at sample X is always processed before a segment starting at X (same-pitch Off before On). **CC / pitch bend**: a clip's events are delivered only inside its audible spans, its current value (latest event strictly before the span — it may lie in a covered gap or before a trimmed window) is restated at every span start (the chase when the winning clip changes), the clip's own audible end keeps the events placed exactly there (a recorded take's pedal release); events beyond the window are not delivered. Hidden clips' events are never sent during a cover; no global All Notes Off / controller reset is used (other rows into the same instrument keep sounding); a controller the winning clip never defines keeps its last delivered value (the sticky-controller rule — recorded takes restate sustain / expression / wheel at their start so they carry their own state). All of this happens at bake time on the message thread; the audio thread only walks pre-sorted lists.
- **Proxies.** Clip stored order is render data now, so the fingerprint serializes clips in stored order and `proxy_fingerprint::kFingerprintSchemaVersion` is **2**. A generation rendered under the additive schema 1 stays **comparable — and Current without a re-render — only when the current content is provably layer-insensitive** (`proxy_playback::comparableFingerprintSchemaFor` → `proxy_snapshot::snapshotIsLayerInsensitive`: per unit no overlapping clips, stored order = plan order, every CC / pitch-bend point inside its clip window at the reference rate; absence of overlap alone is not enough because controller handling changed). The missing-Primary recompute (`computeExpectedFingerprintUnderRecordedConfig`) and the Primary-present verdict both apply it; with the Primary present `ProxyCurrentIdentity::expectedFingerprint` is always the current-schema identity a new render carries (the same value `captureRequest` stamps on a job), while the schema-1 reading travels separately as `publishedComparableFingerprint` and only `ProxyRenderScheduler::destinationState` consults it (`matchesPublished`) — mixing the two readings made every re-render of such a destination end as "identity changed during finalizing" (fixed 1.1.13). Every other schema-1 generation is **stale** under the existing policy: never selected for playback (Secondary or silence), re-rendered only in Auto mode on a machine with the Primary; manual / missing-Primary cases keep the documented stale handling — never Current with a different audible result, no option for the old additive playback, assets / identity / plugin state untouched.
- **Proxy render readiness + publication identity (1.1.14; report `docs/PROXY_RENDER_READINESS_2026-10-05.md`).** `proxy_render::renderProxyDestination` ([`instruments/ProxyRenderExecutor.h`](../src/instruments/ProxyRenderExecutor.h)) now runs `verifyInstrumentReadiness` between prepare and the block loop: the content's distinct notes (`ProxyOfflineSequencer::collectDistinctNoteOns`, after `emitInitialControllerState` in a block of its own) are played into the prepared isolated instance one at a time (0.25 s each, AC-coupled rise criterion, settle under the tail threshold between notes), passes repeat 250 ms apart on the worker (message thread free) until no new note has started answering for three passes; then the instrument settles under the tail threshold (All Sound Off only as a last resort) and the render begins. Bounds: 20 s with no answer, 60 s overall — caps on waiting, not correctness inputs; policy in `ProxyReadinessPolicy` (`ProxyRenderExecutionConfig::readiness`, carried by `ProxyRenderRequest`), outcome in `ProxyRenderResult::readiness` (`verified`, passes, sounding/stimulus notes, wait, flush residual, trace — diagnostics only, never fingerprinted). Why: Groove Agent SE restores its state synchronously but streams its kit asynchronously (~1–3 s); a render started right after `prepareToPlay` produced **digital silence** (the whole asset in a Release build, the first 6–12 s of material in a Debug build) which format/length validation accepted and the scheduler published as Current — the 49.3 s vs 39.0 s "same identity, different length" difference was only the symptom (real 11.3 s cymbal decay vs the 1 s silence window). Its state bytes are volatile (they grow on every `getStateInformation` call), so they are no readiness signal; a fixed delay is not one either. A render whose scheduled notes produced nothing above the tail threshold now fails with `NoAudibleOutput` (never published; the explicit silent generation stays reserved for empty destinations). Publication (`proxy_store::publishRenderedProxy`): the fingerprint identifies render inputs, not bytes — reuse of an existing file under the canonical name requires **identical bytes** (`filesHaveIdenticalBytes`; format + length had accepted a silent file); a non-identical occupant (earlier incomplete render, a sample-level-different render of a non-deterministic instrument, a foreign object or directory) is never overwritten or deleted — the new asset goes to the next free sibling name `track_<id>_<fp>_<n>.wav` (`generationSiblingFileName`) and the metadata names the file in use (`ProxyPublishOutcome::publishedUnderSiblingName`, `collisionNote`). Known, unchanged: VB3-II with the TSE preset parks −4.4 dBFS of DC after any note (organ-dc defect), so its proxy render still fails honestly at the tail cap (`TailLimitReached`) — readiness sees its notes answer (AC-coupled) and reports the flush residual. Diagnostics: `--stability-proxy-render-probe <project> <trackId> <outDir> [--repeat N] [--wait-after-prepare ms] [--publish] [--state-blob <file>] [--no-readiness] [--realtime-indication]` renders one destination repeatedly through the production engine seam with kept artifacts and a content analysis ([`diagnostics/ProxyRenderProbeAnalysis.h`](../src/diagnostics/ProxyRenderProbeAnalysis.h)).
- **Tail-policy v2 — DC-tracked tail detection and resting-level EOF (1.1.15; report `docs/PROXY_TAIL_POLICY_V2_2026-10-05.md`, steering §15.2 / §15.6).** `proxy_render::kTailPolicyVersion` is **2** (threshold −70 dBFS, window 1.0 s, cap 30 s unchanged). `DcTrackingPeakMeter` ([`instruments/ProxyRenderTypes.h`](../src/instruments/ProxyRenderTypes.h)) keeps a one-pole offset estimate per channel (`kTailDcTimeConstantSec` = 0.5 s, coefficient `1 − exp(−1/(τ·fs))`, defined at every rate) and reports the block's raw peak, residual peak `max|x − dc|` (per channel, louder channel wins — no mid-sum) and the offsets at block end; `ProxyTailDetector::feedBlock` observes every block (the estimate is continuous across the music→tail boundary) and decides only in the tail phase on the **residual**, window counted in rendered samples, the straddling block judged whole; `seedDcEstimate` takes the readiness verification's parked offset (its settle and flush use the same meter: `ProxyReadinessOutcome::flushResidualDb` / `flushRawPeakDb` / `parkedDcAtRenderStart`). The executor's plausibility rule is `ProxyRenderResult::maxResidualPeakLinear < threshold ⇒ NoAudibleOutput` (constant offset = no output; the readiness stimulus is excluded), the raw peak stays in the result for diagnostics (`maxPeakLinear`, `dcEstimateAtEnd`, `firstSample`/`lastSample`). The judged quantity is the only thing that changed: no sample of the asset is filtered, faded or normalized. Why: VB3-II with the user's preset parks −0.605 of DC after any note (organ-dc defect); v1 judged |x| and ran into the cap (`TailLimitReached`, nothing published) although the residual was below −70 dBFS 3.9 s after the last note. **Comparability**: `proxy_playback::comparableRenderPoliciesFor` treats a generation recorded under tail v1 (or with no recorded policy versions, read as v1) as comparable with v2 — v1 silence is v2 silence with the same end point — so such generations keep `Current` on load (also without the Primary, the recorded-config recompute uses the recorded policies; with the Primary `publishedComparableFingerprint` is computed under the recorded schema + policies); any other policy drift is `Stale`. Nothing is re-rendered automatically; a manual *Render now* publishes under a new generation name (policy versions are F12) and keeps the old file. **Playback boundary**: `ProxyPlaybackReader` measures each channel's mean over the asset's final silence window at open (`restingLevelAtEnd`, zero when below threshold on both channels) and continues at that level past EOF in `audioThread_fetch` (early return, straddling block, loop-head remainder) and in `convertRangeLinear` (exact copy and sinc paths); the pre-roll stays zero. Measured through the user's Pro-Q 3 10 Hz insert: no step at EOF, past EOF, at a loop wrap or in a mixdown across EOF. **Open**: transport Start/Stop inside an offset region is a 0 ↔ −0.605 step at the proxy boundary (−24 dBFS post-filter at the row's fader) that the Primary (whose offset persists while stopped) does not produce — documented, not fixed (report §6). Diagnostics: `--stability-proxy-render-probe … [--tail-policy-v1] [--retain-failed]` (v1 judging for reproduction, failed artifact kept for analysis) and `--stability-proxy-playback-edges <project copy> <trackId> <outDir>` (stopped / start / EOF crossing / past EOF / Stop / restart / loop wrap / mixdown windows, pre-insert peak + DC L/R via the `PluginInsertHost` level tap, post-strip and Stereo Out meters, proxy vs Primary).

## Track-header column (shared boundary, user-resizable, app-wide persisted)

- **One width for the whole header column.** `TrackLanesView` owns a single runtime value (`getTrackHeaderColumnWidthPx` / `setTrackHeaderColumnWidthPx`) used by every row kind's header (audio, instrument, MIDI, group, master), the lane-area x-origin, the grid, the header-reorder insert line and hit-testing. `applyTransportControlsLayout` reads the same `effectiveTrackHeaderColumnWidthPxForTotalWidth(area.getWidth())` for the ruler inset, the add-track corner button and the `PlayheadOverlay` origin, so all views share the identical boundary x. No per-track widths; names never change the width (they are fitted/truncated inside the header).
- **Limits are derived from the real control layout, in logical (DPI-independent) px** (`track_header_geometry` in [`TrackHeaderView.h`](../src/ui/TrackHeaderView.h), compact-header slice 2026-10-07): group margin 8 (active stripe 0–4, group marker x 5–7) + colour segment `3 + 14 (type icon) + 3 + digits × 7 + 3` (**44 px** for the 3-digit minimum column, 51 for 4 digits) + gap 3 + the three reserved title-row cells `[Power][Mute][Solo]` × 22 px + gap 4 + a name field of at least `kNameMinWidthPx` = 48 px + right pad 8 ⇒ **minimum 181 px** (`kMinimumHeaderColumnWidthPx`); **default 200 px**; maximum 480 px. Narrower names are never the limit: the title is ellipsized inside its field at the unchanged 14 pt.
- **Clamp formula** (`TrackLanesView::clampHeaderColumnWidthForTotalWidth`, pure): preference clamped to `[181, max(181, viewWidth − 160)]` so at least 160 px of lane area survives on narrow windows, and never wider than the view. The preference itself is kept, so the full width returns when the window grows. A width saved by an older build (e.g. the pre-compact-header 154/166) is clamped UP to the new minimum at layout time; a larger saved width is preserved.
- **Drag handle.** A 6 px child component (`HeaderColumnResizeHandle`) centred on the boundary, full height, `LeftRightResizeCursor`, faint highlight while hovered/dragging. It owns its mouse events, so a width drag can never start a clip move, a row-height drag or a header reorder; middle-button pan still works through the parent listener. Each change re-lays out the lanes view and (via `setOnTrackHeaderColumnWidthChanged`) `TransportControlsContent::resized()`; musical clip positions are unchanged (the x↔sample map simply moves with the origin).
- **Persistence is app-wide (machine-local), not project-bound.** [`UiLayoutSettingsStore`](../src/ui/UiLayoutSettingsStore.h) writes `%APPDATA%\MiniDAWLab\ui-layout.xml` (`<UI_LAYOUT><TRACK_HEADER_COLUMN widthPx="…"/></UI_LAYOUT>`) once per completed drag (handle release), never per mouse move; it is loaded in the `TransportControlsContent` ctor before the first layout. Absent / malformed / non-numeric / non-positive ⇒ the default; absurd values are clamped at layout time. Project files keep persisting *project-bound* window state only (main-window bounds, Follow, MIDI editor bounds/workspace). Changing the width is not a session edit: no undo step, no dirty flag, unaffected by adding/removing tracks.

## Current-time / playhead rendering (UI only)

- **One driver per window, and in the main arrangement one *moving layer*.** In the arrangement window, [`PlayheadOverlay`](../src/ui/PlayheadOverlay.h) is the **only** sampler of the shared [`UiPlayheadClock`](../src/ui/UiPlayheadClock.h) (owned by `TransportControlsContent`) **and the only component that draws a moving playhead**: its 60 Hz tick reads one display position per frame, stores it, and draws both the long lane line and the short ruler marker from that one value (see the buffering bullet below — [`TimelineRulerView`](../src/ui/TimelineRulerView.h) draws no marker and receives no per-frame pushes). **No `paint` reads time** — every paint draws only the stored frame value, so an externally triggered repaint (lane content below, window damage) reproduces exactly the column the dirty-rect bookkeeping knows about. Two independent samplers, or re-reading the clock inside `paint`, is what produced stale line columns and per-lane lead/lag. The MIDI editor's ruler stroke and grid line both read the piano roll's own smoothed `uiPlayheadDisplaySamples_`.
- **Smoothed clock.** `Transport::readPlayheadSamplesForUi` is published once per **audio block** (a staircase). `UiPlayheadClock` advances with wall-clock time and applies a small proportional correction (~8 %/tick) toward the published value, monotonic during playback; only real discontinuities (seek, cycle wrap, dropout, > 8192 samples) snap. Chasing every new block value re-anchors onto the staircase and reads as jitter.
- **One mapping and rounding.** Every indicator converts through [`playhead_pixel`](../src/ui/PlayheadPixelMapping.h): `x = originX + (sample - visibleStart) / samplesPerPixel`, then `floor(x) + 0.5` (pixel-centre) so 1–1.5 px strokes stay crisp and land in the same column.
- **Narrow invalidation.** Playhead frame advances invalidate the previous and new pixel column instead of the whole component; a frame that stays in the same column repaints nothing. Structural changes (locators, cycle, zoom/scroll, tempo/meter, ruler mode, bounds) still repaint fully. Lanes must **not** blanket-repaint at playhead cadence: the instrument `MidiEventLane`'s old 20 Hz playing-repaint forced the transparent overlay above it to redraw off-frame and was removed.
- **Timers:** arrangement overlay drives at **60 Hz** (ruler keeps a 30 Hz structural watcher); the piano roll uses **60 Hz** while playing and **6 Hz** idle. No repaint work runs on the audio thread, and none of this affects scheduling or the authoritative playhead.
- **Follow autoscroll is page/event-driven and globally budgeted, never frame-driven.** Both follow implementations (main arrangement in `MainAppWindow`, piano roll in `ExperimentalPianoRollView`) admit viewport pages through a per-window [`FollowAutoscrollGovernor`](../src/ui/FollowAutoscrollGovernor.h) **plus** the process-wide `GlobalFollowWorkCoordinator` (same header), because every follow page forces a full repaint of the scrolled surface. A page is admitted only when *all* hold: (1) the playhead crossed the comfort-band boundary of the current view; (2) follow is re-armed — after a page it re-arms only once the playhead was observed *inside* the band again, otherwise (extent clamp, fine zoom) it drops to a sparse re-arm interval (~750 ms) instead of re-firing every opportunity — the edge condition alone is never a standing pan permission; (3) capacity — the measured frame interval is on time and one clean frame passed since the last page; (4) no recent user viewport gesture in this window (~250 ms holdoff); (5) globally: at most one follow page across *all* windows per 250 ms, and follow in other windows yields ~1 s while the user pans/zooms somewhere (Follow stays visually ON; it just never fights interaction — this is also why a MIDI editor restored with Follow ON cannot overload the main window while the user works there). Wall-clock-only rate limits are forbidden here: wall time elapses *while the thread paints*, so an expensive pan re-arms such a limiter immediately and saturates the message thread (see `MAIN_FOLLOW_ZOOM_UI_FREEZE_FORENSIC_AUDIT.md`). Explicit single-shot moves (seek snap, Follow toggled ON) bypass the gates but register with both objects. The roll additionally skips follow work while hidden/minimised. Main and MIDI editor Follow stay independent (project `mainWindow.followPlayhead` vs per-clip `midiRollFollowEnabled`).
- **The ruler and lane stack are buffered to images; playhead stripes are blits, not paints. This is a load-bearing responsiveness fix — do not remove it.** `TimelineRulerView` and `TrackLanesView` call `setBufferedToImage(true)`, so JUCE caches each fully rendered subtree (ticks/labels/locators; grid + audio lanes + instrument row + headers) and the transparent `PlayheadOverlay`'s ~60 Hz stripe invalidations redraw from the cached image instead of re-running any content `paint`. **Playhead movement must never cause `ClipWaveformView`, `MidiEventLane`, `TrackLanesView`, or `TimelineRulerView` content paints at playback rate.** That steady-state repaint tax — not Follow, not JUCE wheel handling, not the shared clock, not zoom math — was the confirmed root cause of the main-window playback-dependent zoom freeze: the freeze reproduced with Follow OFF and a stable viewport, while the MIDI editor (which has no transparent full-column overlay above its content) stayed responsive under playback + Follow + fast zoom. Consequences future changes must respect:
  - The overlay's bounds include the ruler band, and it draws the short ruler marker segment (`kRulerPlayheadMarkerLengthPx`) plus the long lane line below the band from the same frame value. The ruler must **not** paint a marker or take per-frame pushes: a marker baked into the ruler's buffer goes stale, and per-frame pushes reintroduce the tax.
  - Any code that changes lane or ruler *visuals* must call `repaint()` on the affected component explicitly. A child's own `repaint()` still invalidates the matching region of the parent buffer, so all existing content-change paths keep working — but you can no longer rely on the overlay's stripes happening to expose stale child content, which used to hide missing invalidations.
  - Cost of the design: one viewport-sized ARGB image per buffered subtree, and one extra image copy per full repaint. Both are deliberate and cheap next to the paint storm they replace. History and diagnostics: `MAIN_WINDOW_ZOOM_UI_FREEZE_FORENSIC_AUDIT.md`.
- **Main-arrangement paint work is culled by the dirty clip region.** During playback the transparent `PlayheadOverlay` invalidates narrow stripes at 60 Hz over the whole lane column, and (when a content repaint has invalidated the buffered image, see above) every component under the stripe repaints. All main-window paint bodies therefore bound their content loops by `juce::Graphics::getClipBounds()` (zoom-freeze fix, see `MAIN_WINDOW_ZOOM_UI_FREEZE_FORENSIC_AUDIT.md`): `TimelineRulerView`/`TimelineLocatorPainter` tick/label/grid loops take a cull sample window (musical *labels* still run their full placement loop so stateful spacing decisions match full repaints — only the final `drawText` is culled); `MidiEventLane` skips clips outside the dirty rect, culls note bars by a precomputed tick window, and caches each clip's preview pitch range (invalidated on controller change broadcasts); `ClipWaveformView` has a narrow-stripe fast path that only blits the existing wave raster plus dirty-culled chrome — a stripe paint must **never** sync strips, take the pyramid-cache mutex, or rebuild the raster (raster rebuilds happen only in full repaints, whose coalesced flush always follows any `samplesPerPixel` change; a stripe may thus blit a one-message-batch-stale raster, which is corrected within the same batch). New paint code in the arrangement column must keep stripe repaints O(dirty area).
- **Wave-raster rebuilds are deferred, never run inside paint for geometry changes.** `ClipWaveformView::paint` rebuilds its overscanned raster synchronously only when it has *no* raster yet or the *content* fingerprints changed (strips/pyramid — rare, correctness-first). Zoom (`samplesPerPixel`), pan beyond the overscan margin, and resize instead take a stale-blit path: `blitWaveRasterApproximate` maps the current visible range onto the old raster's coverage and draws it scaled (uncovered regions stay background, never stretched garbage; the mapping degenerates to a pixel-exact 1:1 blit in steady state, and the stripe fast path uses the same helper so stripes stay aligned while a rebuild is pending). Each stale paint restarts a per-lane one-shot timer (~200 ms, staggered ~35 ms per lane at construction), so an active wheel gesture rasterizes **zero** intermediate zoom levels and each lane rebuilds exactly once — for whatever the viewport says when the timer fires (the restart *is* the stale-generation guard) — in its own message-loop turn. Rebuilds also reuse the existing image allocation when dimensions are unchanged. This removed the remaining zoom-freeze spike: previously every wheel step's coalesced full repaint rebuilt (and reallocated, ~1.4 MB) every audio lane's raster synchronously in one turn.
- **Known visual tradeoff (accepted): waveforms are approximate during active zoom/pan.** While the user is zooming or panning the arrangement, audio lanes show the previous wave raster scaled to the new mapping, so waveforms can look slightly blurry or soft, and a rapid zoom-out can briefly show a clipped waveform where the old raster does not cover the new visible range. After ~200 ms of viewport idle each lane rebuilds once and the display becomes correct. This is intentional: it is what keeps the message thread responsive during zoom, and it is releaseable for current DAL goals. Improving waveform fidelity *during* the gesture (e.g. a background rasterizer or multi-resolution pyramid blit) is future polish, not a correctness blocker — a stale waveform that never refreshes after idle **is** a bug.
- **User viewport repaints are coalesced per message batch.** Wheel zoom/pan and drag-pan handlers must not call `repaint()` per input event: under a fast gesture the OS interleaves forced window repaints with the queued input events, so per-event dirty-marking costs one full recomposition *per event* and freezes the message thread for many seconds (the second follow-freeze root cause). Viewport *state* is applied immediately per event (geometry stays exact), but dirty-marking goes through [`CoalescedRepaintFlusher`](../src/ui/CoalescedRepaintFlusher.h) (a `juce::AsyncUpdater`): the main window flushes ruler + lanes + instrument row once per batch from the `TimelineViewportModel` listener, and the piano roll flushes its own full-roll repaint the same way. Follow pages flush synchronously (their frame tick already paints that turn).

- **Structural track steps share one application rule (1.1.19).** A Delete Track step and a Duplicate Track step have the same shape (timeline `before` / `after` snapshots + `PluginUndoStepSides` for the row's insert chain + `InstrumentTrackDeleteUndoSides` = the captured instrument project row). On undo **and** redo the coordinator applies the snapshot, then the chain sides, then `applyInstrumentTrackRuntimeSides`: **if the restored timeline contains the row, the instrument runtime is recreated from the captured row** (`TrackLanesEditCoordinator::restoreDeletedInstrumentTrackForUndo` — the project-load restore path), **otherwise it is retired** (`redoTeardownDeletedInstrumentTrack`, the hardened delete teardown). Presence decides, not the step kind. Every recorded edit and every undo / redo is refused while a staged project load owns the session (`Callbacks::isProjectLoadInProgress`).

## Project loading is staged and message-loop driven (1.1.19)

- **Why.** The 100-track load test showed an 18 s "Not responding" tail after `load: complete`: the whole model was applied synchronously (every clip decoded again), 64 instruments were restored in one loop, and the insert chains (50, with 18 AmpliTube 4 instances at 1–2 s each) were restored in ONE deferred `callAsync` — a 19 s continuous block of the message thread after the window already looked loaded.
- **Shape.** [`ProjectIoCoordinator::loadProjectFromFile`](../src/app/ProjectIoCoordinator.h) runs a `LoadJob` through units: **ParseAndDecode** (background `std::thread`: `readProjectFile` + every *unique* audio file decoded once into `Session::PreDecodedMaterialByPath`, progress posted via `callAsync` guarded by the coordinator's `AsyncLifetimeOwnerToken` **and** the job serial), **ClosePrevious** (transport stop, Monitor off, `onProjectAboutToBeReplaced`, the instrument processing gate, previous runtimes retired), **ApplyModel** (`Session::applyLoadedProjectModel` with the pre-decoded material; insert chains are *handed back* instead of scheduled; the routing plan is rebuilt immediately so the callback never runs the restore phases with the previous project's plan), **RestoreInstrument** (one row per unit — the same per-kind logic as before), **OrphansAndUi**, **RestoreInsertChain** (one chain per unit, `importChain`), **Finalize** (`onProjectLoaded`, mark clean, window bounds, MIDI editor workspace, info dialog). Two drives: **Interactive** (the user's File > Open) schedules one unit per message-loop turn through `juce::Timer::callAfterDelay(4)` with an *announce-then-execute* pattern so the progress text paints before the unit runs; **Synchronous** (stability test mode) runs the same units in a loop so every scenario keeps the "load returns loaded" contract. No nested message loop anywhere.
- **Progress window.** `LoadProgressWindow` (a modal `DialogWindow`, no close) shows the phase ("Reading project…", "Loading audio material… 3 of 7: file", "Closing previous project…", "Preparing project…", "Loading instruments… 17 of 64: VB3-II", "Preparing tracks…", "Restoring effects… 9 of 50: AmpliTube 4", "Finalizing project…"), a detail line and a `ProgressBar` that is **determinate only where a count is known** (fraction = done / total, never 100 % before completion) and indeterminate for single operations. Modal state refuses mouse input to the main window; the main window keeps painting (`performAnyPendingRepaintsNow` after each update plus the normal loop between units).
- **Gates while a load runs** (`isLoadInProgress()`): `isProjectDirty()` is false, periodic autosave is blocked ("project load in progress"), Save / Open are refused, undo / redo / every recorded edit are refused in `UndoRedoCoordinator`, the structural-edit predicate (header menus, clip edits, add-track button and menu, Power) is blocked, `TransportPlayPauseStopController` refuses to start Playing, and `RecordingCoordinator` refuses a Record start with a clear text (`setRecordStartBlockedPredicate`). The instrument processing gate is held for the whole load; insert chains are published per track as they come up (publish-before-destroy as always).
- **Lifecycle.** The worker posts only through the lifetime guard + job serial, so a destroyed coordinator or a newer load never receives stale results; the unit timer checks pointer **and** serial. Completion and failure both go through `loadJob_finish` (progress window closed, completion continuation fired — the autosave recovery prompt uses `loadProjectFromFileThen` —, gates released, error alert; in stability mode the alert is logged instead). A parse failure happens before anything of the previous project is touched, so the previous project stays intact. Closing the main window during a load: the dialog's modal state makes JUCE ignore the main window's close button and `WM_CLOSE` until finalize; a forced quit destroys the coordinator, whose destructor joins the worker, releases the gate (job destructor order) and drops the dialog — the lifetime guard keeps late callbacks from touching anything.
- **Measured (Release, 100-track copy, `--stability-load-progress`):** 45 s total with the window updating through every phase; the longest message-loop gap is **≈ 2.2–2.5 s** and sits on the first AmpliTube 4 instantiation ("Restoring effects… 1 of 50") — a single third-party operation DAL cannot split; no gap reached the 5 s "Not responding" threshold (22 gaps > 0.5 s, all plug-in instantiations / state restores). **Remaining limitation:** retiring a loaded 100-track project when opening another one (`clearExperimentalInstrumentRuntimes`, 64 hosts) is one 15 s synchronous unit, announced as "Closing previous project…"; splitting that teardown per row is backlog.

## Arrangement vertical scrollbar (1.1.19)

- **One scroll model.** `TrackLanesView` keeps the single vertical offset (`verticalScrollOffsetPx_`) that lays out headers *and* lanes in `resized()`; the wheel, the scrollbar and programmatic scrolling all go through `scrollVerticallyToOffsetPx` (same clamp). The view publishes `VerticalScrollModel { contentHeightPx (sum of the laid-out row heights — varying heights included), viewportHeightPx (height − timeline gutter), offsetPx }` and fires `setOnVerticalScrollModelChanged` after every layout in which it changed (resize, wheel, row-height drag, track add / duplicate / delete, undo / redo, project switch).

## Arrangement track headers: compact layout, row-height grid and track colours (2026-10-07)

- **Header structure (every row kind, every height)**, left → right ([`TrackHeaderView`](../src/ui/TrackHeaderView.h), geometry constants in `track_header_geometry`): an 8 px **group margin** (the 4 px active-track stripe at x 0–4 and the 2 px visual-group member marker at x 5–7 live here, outside everything else) → the **colour segment** spanning the full chrome height (type icon 14 px + right-aligned 1-based arrangement number at 11 pt, width `3 + 14 + 3 + digits × 7 + 3`, at least 3 digits, one common digit count for the whole column = `max(3, digits of the track count)`) → gap 3 → the **title row** (y 2, 22 px cells): `[Power][Mute][Solo]`, present cells collapsed left, the three slots always reserved so the name column starts at the same x for every kind (Group rows `[Mute][Solo]`, Stereo Out `[Mute]` only — unavailable cells have EMPTY bounds, no hit area and no tooltip) → gap 4 → the **name** (same 14 pt, ellipsized, never shrunk; Instrument / MIDI rows keep a 9 px slot at the right end for the live-MIDI activity dot so the ellipsis never jumps) → right pad 8. A **second control row** (y 27) carries `[Monitor][Arm][Instrument editor][Alternatives]` (present cells collapsed left) and exists only when the row height is ≥ `kMinimumHeightForSecondRowPx` = 53 px; hidden rows mean empty bounds — hiding never changes any state. The 4 px bottom **resize band** is kept at every height (hit order: band first, then cells, then plain-click activation / shift-selection / reorder), so Micro rows can still be resized without stealing button clicks. Painting, state and command paths of Power / Mute / Solo / Monitor / Arm / editor / alternatives are the pre-existing ones (`TrackStripButtonGlyphs`), only their placement changed.
- **Type icons** (`track_strip_glyphs::TrackTypeIcon`, vector-drawn in `drawTrackTypeIcon`): Audio = waveform bars, Instrument = keyboard, MIDI = DIN connector, Group bus = merging lines, Stereo Out = two rings. The **number** is the current arrangement order (not the `TrackId`), refreshed with every insert / duplicate / delete / reorder and counting hidden collapsed members; it is display-only and never stored. A visual (collapsible) group has no number of its own.
- **Row-height grid.** [`ui/TrackRowHeightPresets.h`](../src/ui/TrackRowHeightPresets.h) is the ONE place the vertical geometry lives: `height = kMicroRowHeightPx + n × kRowHeightStepPx` with **Micro = 28 px** (n = 0: top pad 2 + one 22 px title row + 4 px band — derived from the real header chrome and `static_assert`ed), **step = 14 px** (half a Micro row), **Mini = 42** (n = 1, the same single row with air), **Small = 56** (n = 2 = two stacked title rows: title row + second control row; alternatives / editor cells may still hide when the second row has no room), **Medium = 98** (n = 5, ≈ the old 96 default), **Large = 196** (n = 12 ≈ 2 × Medium). `kMinRowHeightPx` = 28; the old 480 px *user* cap is gone — only a documented safety cap `kRowHeightSafetyMaxPx` = **1120** (n = 78) remains, so heights above Large are ordinary grid steps. `LaneEventDetail` thresholds live next to the heights: lane heights < 32 px paint **Bars**, < 48 px **Compact**, otherwise **Full** (so Micro = Bars, Mini = Compact, Small and up = Full).
- **Snapping resize.** The bottom-edge drag computes `snapRowHeightPxToGrid(startHeightOfTheDrag + totalPointerMovement)` (round to nearest step, ties up) — a pure function of the pointer, so moving back and forth is stable and every intermediate height is on the grid; the drag-end snap is then a no-op. `applyTrackRowHeightsFromLoadedProject` only **clamps** (`clampRowHeightPx` to [28, 1120]): heights saved by older builds (64 / 96 / 192 …) stay exactly as saved and read as Custom until the first resize or preset re-snaps them.
- **Presets.** The toolbar dropdown lists **Micro / Mini / Small / Medium / Large** (`displayNameForPreset`, keys `micro | mini | small | medium | large`); **Custom** is status only. `applyTrackRowHeightPreset` sets EVERY row's *normal* height in one gathered `resized()` pass — including hidden members of collapsed groups (their 4 px display is untouched, the new normal height shows on expand) — clears individual overrides and becomes the default for NEW tracks; Duplicate copies the SOURCE row's height. The status is derived from normal heights only (`presetMatchingHeightPx`), so collapsed strips never read as Custom.
- **Event painting at low heights** (`ClipWaveformView` audio lanes and the instrument / MIDI `MidiEventLane`, both via `laneEventDetailForHeightPx(getHeight())`): **Bars** = a thin `kLaneBarFieldHeightPx` = 8 px field per event showing its real time extent (no waveform, notes or text; selection outlines the bar); **Compact** = the rounded event body only; **Full** = the unchanged waveform / note preview + name label + overlap hatch. Painting only — hit geometry, trim handles, drag/drop, clip functions and the musical data are the same at every height; the collapsed-group grey overview is a different (group) painter.

## Collapsible track groups (visual)

- **Purely visual.** A group ([`domain/VisualTrackGroup.h`](../src/domain/VisualTrackGroup.h)) is layout metadata over **adjacent arrangement tracks** — NOT the routing Group-bus track kind. Creating/renaming/collapsing/ungrouping never publishes a `SessionSnapshot`: track order, clips, routing, sends, plugins, instruments, proxy identity, Mute/Solo/Off/Monitor/Arm, playback, recording, export and mixer visibility are untouched by construction. State lives on `Session` OUTSIDE the snapshot (exactly like the Solo sets): stored member lists tolerate stale ids of deleted tracks, so undoing a track deletion restores membership for free; the *effective* membership filters to the current snapshot, and a group is **displayable** only while ≥2 effective members are contiguous in snapshot order (otherwise its rows render as normal tracks — the universal safe fallback). Groups never nest or overlap and never contain Stereo Out.
- **Creation (header multi-selection).** Plain header click selects one row, shift-click selects the contiguous visible range from the anchor (`handleHeaderSelectionClick` in [TrackLanesView](../src/ui/TrackLanesView.h); wash + 2 px marker painted by `TrackHeaderView`). The selection is UI-only — never the active track, never clip selection, and there is deliberately NO mouse-down+drag header selection (that gesture stays reorder). Right-click inside the selection keeps it; outside selects the clicked row (`applyHeaderRightClickSelectionPolicy`). Every header context menu (audio / group-bus / instrument / MIDI rows) appends **"Create collapsible group…"**, enabled only for ≥2 adjacent ungrouped non-master tracks; an async name prompt (default `Group <n>`) feeds `Session::createVisualTrackGroup`, which re-validates and creates the group expanded with every height untouched. Delete/Duplicate stay single-track commands.
- **Expanded look + handle.** Members carry a discreet vertical marker at the header's left edge (right of the active-track stripe, never covering buttons). The **"inverted golf club" handle** (`VisualGroupHandleView`, a small overlay child of `TrackLanesView`) extends the marker into a short tab at the boundary between the first member and the previous track, showing the collapse glyph + name; since the compact-header slice its placement adapts to the neighbouring row heights (gutter band / inline in the previous row's free chrome / compact 12 px tab confined to the margin + colour segment — see the track-header section), it stays visible in the gutter band while the group intersects the viewport (so it works for a group at the very first track and while scrolled), unmaps when the group is fully scrolled out, and swallows its mouse events (the previous track and its resize band are unreachable through it). Short click = toggle collapse; **long press (500 ms**, cancelled by >4 px movement**) = inline rename** (Enter commits, Escape cancels, no toggle at mouse-up); right-click = Expand/Collapse, Rename, Ungroup (Ungroup removes only the metadata).
- **Collapsed mini-view.** Each effective member becomes a strip of **exactly `kCollapsedGroupMemberRowHeightPx` = 4 logical px** (the Micro 28 px minimum and the height grid deliberately do not apply to the DISPLAY), zero gap (row separators inside the run are suppressed), same member order. `rowHeightForVisibleEntry` returns the display height while `rowHeightForTrack` keeps the stored NORMAL height — all layout/paint/scroll/diagnostic call sites share the former, while save / preset status / duplicate / resize use the latter, so 4 px can never leak into persistence or the Custom status, and a global preset chosen while collapsed changes the hidden members' normal heights for the next expansion. Strips are **painted** (`paintCollapsedGroupContent`), not components: grey interval fields (`0xff8e98a8`) for the row's own clips (audio placements with effective trim lengths; instrument/MIDI rows their own timeline clips — a clean routed-to destination shows nothing), using the exact `TimelineRulerView::sessionSampleToLocalX` mapping as the full lanes. Collapsed member rows get EMPTY component bounds in `resized()` (the scrolled-out-row mechanism), so there are NO hidden buttons, click areas or tooltips under the strips. The group's top edge anchors on collapse (offset preserved, then the normal clamp), and the ONE shared vertical scroll model (`verifyVerticalScrollLayoutForDiagnostics` treats collapsed members as expected-empty) keeps scrollbar and alignment exact.
- **Membership on track changes.** Duplicate of a member inserts the copy right after its source in the group; deletion drops the member from the effective view (snapshot restore brings it back); below 2 effective members the group dissolves visually and returns the same way. Reorders are checked by `Session::checkTrackMoveAgainstVisualGroups` (simulated splice; every displayable group must stay contiguous): the header drag shows the red no-op line, the drop is refused with an alert naming the group + the Ungroup hint, and `Session::moveTrack` no-ops defensively — the audio-model order can never diverge from the visible order. Within-group reorders pass.
- **Persistence + undo.** v27 `visualTrackGroups` (see the schema section). Create / Rename / Ungroup run through `UndoRedoCoordinator::executeUndoableVisualTrackGroupsEdit` — ONE narrow metadata step (full group list before/after, same timeline snapshot pointer on both sides; identical lists record nothing) that can never revert clips, tracks or a take. Collapse/expand is a display change: `markProjectDirtyFromEdit` only, **no undo entry**.
- **Verification**: `CollapsibleTrackGroupFocusedTests` (see [DEVELOPMENT_TEST_POLICY](DEVELOPMENT_TEST_POLICY.md)); feature report [`COLLAPSIBLE_TRACK_GROUPS_2026-10-07.md`](COLLAPSIBLE_TRACK_GROUPS_2026-10-07.md).

## Duplicate Track (1.1.19)

- **Command.** "Duplicate Track" sits right after "Delete Track" in every header context menu (audio / group in `TrackLanesView`, instrument / MIDI-content rows in `InstrumentTimelineRowCoordinator`), carries the **clicked** `TrackId` (never the active track) and is disabled with an explanatory text while structural edits are blocked (recording, count-in, playing, project load). The handler is `TrackLanesEditCoordinator::duplicateTrack(sourceTid)`; Stereo Out is refused by the domain.
- **One undo step with the Delete Track shape.** Inside `executeUndoableTrackDelete("Duplicate track", …)`: (1) under `ScopedTrackDeleteRealtimeGate` the source's insert chain (`exportChain`) and — for instrument / MIDI-content rows — its project row (`buildExperimentalInstrumentProjectBlock`: live Primary state when capturable, retained state otherwise, Secondary config + state, proxy metadata, update mode, clips with notes / CC / pitch bend) are captured, so no state call overlaps a worker processing the instance; (2) `Session::duplicateTrack` → `SessionSnapshot::withTrackDuplicated` inserts the copy directly below the source with a new `TrackId`, new `PlacedClipId`s (`PlacedClip::withId`, same shared material — no WAV copies, same placement / trims / window), the same fader, pre-gain, pan, Mute / Off, output routing, sends, input assignments, MIDI To / channel, and a unique name ("<name> — kopia", then " 2", " 3" …); (3) `importChain(newId, chain)` instantiates **own** plug-in instances (unavailable plug-ins stay placeholders with identity + state bytes) and the step's `pluginSides` are `{newId, {}, chain}`; (4) the captured row is re-keyed to the new id and restored through `restoreDeletedInstrumentTrackForUndo` (the same path project load and Delete-Track undo use — own host, state restored, placeholder shell when the plug-in cannot load); (5) the copy becomes active; Monitor and Record Arm are runtime-only and start **off**. Undo removes the copy (chain evicted, runtime retired — the source keeps its instances), redo restores it with content and own instances; the project is dirty only after success; nothing points at the copy (feeding tracks are neither copied nor rerouted; a MIDI copy keeps the same MIDI To; an instrument copy gets its own instrument).
- **Proxy status of an instrument copy.** The proxy metadata (generation id, path, fingerprint schema) is copied verbatim and evaluated **honestly** by the existing policy: on a machine where the Primary loads, the copy plays its Primary like the source; where it does not, the copy's generation is judged by the same fingerprint rules as the source's (Current only if provably current). Duplicating never fabricates a Current status, never changes the source's generation or file, and schedules no render beyond the existing policy — a re-render of the copy publishes under the copy's id.
- **Verification**: `TrackDuplicateFocusedTests` (domain step: position, name, ids, shared material, settings, routing / sends, refusals, Master invariant) and `--stability-duplicate-track <copy>` (audio row with AmpliTube 4 + a Post insert + a send to a Group, instrument row with clips + state, pure MIDI row routed to an instrument, Group, a row with an unavailable placeholder, own instances + parameter independence, one undo step / undo / redo, dirty flag, save / reload, duplication of a non-active row, the scrollbar checks, PNG evidence of the header menu).

## Power (Off) vs Mute

- **Power / Off** is **structural** (`Track::trackOff_` in the snapshot): engine skips the lane. It **must not** toggle while **playing, recording, or count-in** (UI no-op; no session write).
- **Mute** is **realtime** (`trackMuted_`): effective silence while still running the lane’s processing path as designed. For **instrument rows** this is enforced since 1.1.9: `PlaybackEngine` (realtime and offline loops) and `renderInstrumentPostStripToStereoScratch` treat mute — and a fader at −∞ — as a **gain of 0 after the host has processed the block**, never as "skip the host". Pre-1.1.9 the muted row was skipped before `audioThread_processBlockAndAddToOutputs`, so the MIDI scheduled for it every block accumulated in the host's per-block buffer (audio-thread growth), was fired as one stale burst on unmute and the plug-in was frozen mid-state (its tail / DC and any held notes resumed exactly where they stopped). Only **Off** skips the host.
- **Power visuals** reflect only real On/Off: **On = green**, **Off = grey**. Do not add a third “locked” dim state for power.

**Steering history:** [status/DECISION_LOG.md](../status/DECISION_LOG.md) (2026-05-01 — Track Off vs Mute).

## Solo and Solo memories (temporary listening layer; report `docs/SOLO_AND_SOLO_MEMORIES_2026-10-07.md`)

- **Model.** Solo is a temporary LISTENING layer on top of the stored Mute flags — stored `Track::isMuted()` is never rewritten or reconstructed. `Session` owns **five separate sets** of explicitly soloed `TrackId`s: ONE temporary set plus FOUR persistent memories (buttons 1–4). Exactly one set is *current*: no memory selected (index −1) → the temporary set; memory selected → that memory. The S buttons always show and edit the current set. Solo is ACTIVE only when the current set contains ≥ 1 track existing in the snapshot (`Session::isSoloActive`); a selected but empty (or fully stale) memory restricts nothing. Solo state lives beside `activeTrackId_` (message-thread-owned, not in `SessionSnapshot`), whole-session undo snapshots never carry it, and `resetTransientSoloStateForProjectLoad` clears the transient parts on load while the load path assigns the four memories from the file (v25 `soloMemories`).
- **Mute lock in the command path.** While solo is active, `Session::setTrackMuted` REFUSES every change (and `InstrumentTrackController::setMuted` checks the same `isMuteChangeLockedBySolo()` before flipping its own `muted_`, so controller and session cannot diverge). Project load and undo restore stored mute flags through snapshot replacement, which never passes through the command and is never blocked.
- **Derived engine view.** [`SoloMuteView`](../src/engine/SoloMuteView.h) is derived on the **message thread** (`solo_mute_view::deriveSoloMuteView(snapshot, currentSet)`, pure) and published to `PlaybackEngine` behind an atomic shared_ptr (`publishSoloMuteView`), same release/acquire discipline as the session snapshot; the audio callback (and the offline mixdown loop) acquires ONE view per block — a consistent picture at the block boundary — and performs only allocation-free binary-search lookups. Per track the view answers **ForcedAudible** (explicit solos — heard even if base-muted —, every bus the soloed signal needs downstream incl. enabled send destinations and their chains, the destination Instrument strip of a soloed MIDI lane, and the soloed MIDI lane itself), **PassStoredMute** (upstream feeders of a soloed Group, transitively across buses and send paths — group solo means "hear what the group currently plays", so base-muted feeders stay silent and derived pass-through is never a red S), or **ForcedSilent** (everything else: gain 0 at that track's OWN strip, exactly like Mute — inserts/instruments keep processing per the 1.1.9 "never skip the host" rule, so un-soloing restores the base picture instantly). Off always wins — solo never opens an Off row. Because unrelated sources are zeroed at their own strips, a shared bus carries only soloed signal (no leakage).
- **MIDI gating.** Strip zeroing cannot separate several MIDI sources feeding ONE instrument, so the view carries two suppression sets consumed by `InstrumentTrackController::audioThread_scheduleTransportMidiForSegment`: `suppressOwnTransportClips` (instrument strips open only as a CARRIER for a soloed MIDI source — their own timeline clips must not leak) and `suppressRoutedMidiSources` (MIDI lanes whose routed events must not sound at an open destination). Suppression flushes that source's pending note-offs first, then skips new events — no hanging notes, never a global All Notes Off. A `soloForceAudibleOverridesMute` flag (fed by `trackForcedAudibleBySolo`) makes a base-muted but explicitly soloed Instrument/MIDI lane deliver its events through `playbackEnabledIgnoringMute` without touching the stored flag. Solo gate transitions count as segment discontinuities (CC re-chase).
- **App layer.** [`SoloCoordinator`](../src/app/SoloCoordinator.h) owns the commands (toggle S, memory button semantics: click inactive memory → activate; click another → switch directly; click the active one → back to the temporary set; nothing ever copies between sets), re-derives + republishes the view after every solo command, after undo/redo of a solo step, and when it observes a new session snapshot pointer (10 Hz pointer compare — snapshots are published from ~40 sites, so the coordinator watches rather than hooking each one). S edits of an ACTIVE MEMORY are wrapped in `UndoRedoCoordinator::executeUndoableSoloMemoryEdit` — ONE narrow undo step carrying only that memory's before/after id sets (same timeline snapshot on both sides, so undoing a solo step can never revert clips, tracks or a committed take; undo targets the intended memory even after switching). Temporary-set edits and memory switches are not undoable and not dirty.
- **Proxies.** Soloing a whole destination may keep playing its proxy. PARTIAL isolation of one source into a proxied destination needs a live path: `ProxyPlaybackCoordinator` gained a `soloIsolationRequested` dependency that (like live monitoring / recording) overrides a Proxy decision to SecondaryLive **when the Secondary is usable**. Temporary solo never changes stored proxy identity/currency and never schedules a render; when partial isolation is impossible (no usable Secondary), the solo toggle is refused atomically with an explanatory alert — never a half state.
- **UI.** `TrackHeaderModel` carries `soloAvailable/soloed/soloSilenced/muteLockedBySolo`; one app seam ([`SoloUiHooks`](../src/ui/SoloUiHooks.h), built once in `MainAppWindow::makeSoloUiHooks`) feeds arrangement headers, instrument/MIDI timeline rows AND mixer strips, and S/M rendering is shared in [`TrackStripButtonGlyphs.h`](../src/ui/TrackStripButtonGlyphs.h): red S only for EXPLICIT membership; the M cell shows the effective state — normal mute (clickable), solo-silenced (distinct dimmed tint), or passed-through — with a small drawn padlock while Mute is locked (clicks inert, the M letter stays readable). No S on Stereo Out. The four memory buttons live in [`SoloMemoryStrip`](../src/ui/SoloMemoryStrip.h) (main window only), laid out by `TransportLayoutHelper` in the edit-tool toolbar band directly above the track-header column, aligned with it and following its width (fits at the 154 px minimum). The mixer strip width grew 150 → 174 px for the 7-cell button row.

## Main output routing (implemented)

**Plan reference:** [routing_mixbus_master_plan](../../.cursor/plans/routing_mixbus_master_plan_08949036.plan.md).

- **Output routing** (`Track::routedOutputTrackId_`): every non-Master row routes its **main/dry** signal to **Stereo Out** or a **Group**. Groups may nest (e.g. Drum Group → Mixbus → Stereo Out). Validation prevents cycles ([`SessionRouting`](../src/domain/SessionRouting.cpp)).
- **Engine:** [`RoutingPlan`](../src/engine/RoutingPlan.h) + [`RoutingPlanBuilder`](../src/engine/RoutingPlanBuilder.cpp) build a topological bus order (child groups before parents, Master last) and preallocated bus scratch pointers. The audio callback **does not** solve the graph or allocate; it walks `sourceSteps` and `busSteps` only ([`PlaybackEngine`](../src/engine/PlaybackEngine.cpp)).
- **Sources** (Audio / Instrument) render into the scratch for their **output** destination bus. **Group** buses sum incoming scratch, apply their channel strip, and forward to their output bus. **Master** is the unique hardware sink.
- **Mixdown parity:** offline render uses the same `RoutingPlan` path as live playback.
- **UI:** Inspector **Output** dropdown lists legal Master + Group targets. Group/Master rows cannot host clips or recording; Group headers are bus-style (mute-only strip, no record arm).
- **Persistence:** v14 `tracks[].output.trackId` in [ProjectFile.cpp](../src/io/ProjectFile.cpp).

| Piece | Role |
|--------|------|
| `TrackKind::Audio` / `Instrument` | Sources; main output → Master or Group |
| `TrackKind::Group` | Internal bus; output → Group or Master; acyclic nesting |
| `TrackKind::Master` | Unique final sink to device / mixdown |
| `RoutingPlan` | Immutable plan: source steps, bus steps, bus scratch pool |

**Still deferred (routing-adjacent, not sends):** sidechain, PDC, multi-output instruments. Per-track **Input** exists for both domains now: the audio input assignment (v23) and the live MIDI input (v24, see [Live MIDI input](#live-midi-input-monitoring-and-recording)).

## Sends V1 (planned)

**Plan reference:** [sends_fx_reverb_plan](../../.cursor/plans/sends_fx_reverb_plan_9fa7a092.plan.md). **Not yet in code** at the time of this writing; domain/engine/UI slices follow this doc.

### Mental model

- **Output routing** decides where the channel’s **main/dry** signal goes.
- A **send** is an **additive, level-controlled copy** of the channel’s finished post-channel-strip stereo, scaled by send amount and summed into a **destination Group** bus. Sends do **not** replace or reroute the dry path.

Example: Lead Vocal dry → Vocal Group → Mixbus → Stereo Out; simultaneously Lead Vocal send → Plate Reverb Group → Mixbus → Stereo Out.

### V1 rules

| Topic | Rule |
|--------|------|
| Send sources | `TrackKind::Audio`, `Instrument`, **Group** |
| Send destinations | Existing **Group** rows only (FX/Reverb bus = normal Group by convention: user names it, puts plugins on Group inserts, routes Group output via existing output routing) |
| Master | **Never** sends; **never** a send destination |
| Data model | Variable-length `std::vector<TrackSend>` per non-Master row (no fixed slot cap in domain or JSON) |
| Tap point | **Post-channel-strip:** Pre inserts → fader / mute / off → Post inserts → pan → **send tap** → dry bus + each enabled send destination |
| Amount | Linear `[0, 2.0]` stored as `amountLinear` (unity = 1.0, max ≈ +6.02 dB); UI presents **dB** (`-inf` at 0, `0.00 dB` at unity) |
| Validation | Combined **output + send** DAG must stay acyclic; UI and Session setters reject cycle-creating destinations |
| Engine | `RoutingPlan::SourceStep::sends` and `BusStep::sends`; topo over output **and** send edges; one shared **post-channel-strip stage scratch** per step (render once, add to dry + each send dest); no audio-thread allocation or graph solving |
| Mixdown | Same send path as live playback |
| Persistence | **v15** additive: `tracks[].sends[]` with `{ destTrackId, amount, enabled, tap: "postChannelStrip" }` (omit key when empty; do not use `"postFader"` — ambiguous about Post inserts / pan) |

### Inspector (planned UI)

Section order (top → bottom), mirroring signal flow:

1. Track name / kind  
2. Channel volume  
3. Pan  
4. Output  
5. Inserts (Pre, Post)  
6. **Sends** (below Inserts)

- Visible on Audio, Instrument, Group. Hidden on Master.
- **Four fixed visible send rows** bound to the first four entries in the variable list; empty rows show `(none)`; sends beyond row 4 may persist and process but need not be fully editable in V1.
- No track-header send controls. Since 1.1.16 the same four slots are also edited in the mixer strips (same `TrackEditActions`, same validation); the Inspector and the mixer show the same rows.

### Explicitly out of scope for sends V1

PDC, sidechain, send automation, pre/post tap toggle, multi-output instruments, per-track input routing, MIDI editor / snap changes, new `TrackKind::Fx`. (The mixer view exists since 1.1.16 — see [Mixer window](#mixer-window-1116-report-docsmixer_window_2026-10-06md); it adds no send modes or signal paths.)

## Audio mixdown export lifecycle (WAV / MP3)

- **Blocking on the message thread, by design.** `exportStereoMixdownWavBlocking` / `exportStereoMixdownMp3Blocking` ([AudioMixdownExporter.cpp](../src/app/AudioMixdownExporter.cpp)) render the active loop through `PlaybackEngine::renderOfflineMixdownBlock` behind the depth-counted offline render gate and return only when the result file is in place. Nothing else on the message thread — session edits, plugin lifecycle, autosave, device changes, project switch, quit — can interleave with the offline render, because the message loop is not spinning. Project switch / quit *during* an export is therefore impossible by construction; that is the established policy, not an omission.
- **The only UI alive during an export is [`AudioMixdownProgressWindow`](../src/app/AudioMixdownProgressWindow.h).** It paints synchronously and services **only its own HWND's** queued messages (`PeekMessage` with an explicit window handle): paint, mouse, keyboard, activation. JUCE's internal message window (timers, `callAsync`) and every other DAL window stay queued until the export returns. The window pins JUCE's **software renderer** for itself: JUCE 8's default Direct2D peer only defers `WM_PAINT` and draws on a vblank message that cannot arrive while the export owns the thread (and its `performAnyPendingRepaintsNow()` is a no-op) — that was the pre-1.1.5 "white box".
- **Phases and progress.** `MixdownProgressSink::setMixdownProgress(text, fraction)` reports `Rendering... NN%` (measured from the render loop), `Encoding MP3... NN%` (LAME's own console percentage, drained by [`Mp3LameEncoder`](../src/app/Mp3LameEncoder.h); CBR size estimate before the first status line) and `Finalizing...` (indeterminate: writer close + destination replace). "Complete" is only reported after the destination has been replaced.
- **Cancel is cooperative.** The sink's `isMixdownCancelRequested()` is polled between render blocks and during the encoder wait; a cancel terminates LAME, removes the export's own working files and returns `Export cancelled.` — the destination is never touched. The dialog shows an info alert, not an error.
- **Working files vs results.** The user's export folder receives exactly one file. The WAV render temp is a uniquely tagged sibling of the destination (same-volume rename on success); the MP3 pipeline's intermediate WAV lives in the **system temp folder** (`DAL-mixdown-<hex>.wav`) and the LAME output is a tagged sibling (`.__dal_mp3_encode_<hex>.mp3`). All are removed on every exit path by scope guards; nothing else is ever deleted (no sweeping of foreign files).
- **LAME child process.** Its console pipe is drained continuously on a small helper thread (`LameConsoleDrain`) so LAME can never block on a full pipe — the pre-1.1.5 hang; the drained text also feeds progress and error messages. Timeout (10 min) is a safety net only. `--stability-mixdown` asserts the exact result file set and the absence of DAL working files in temp; `--stability-pregain` measures pre-gain on the realtime and offline paths.
